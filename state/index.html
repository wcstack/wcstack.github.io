Which core? #

wcstack ships two reactive cores that drive the same wc-bindable I/O nodes. Pick the one that matches where your logic lives.

wcstackには同じwc-bindableタグ群を駆動する2つのリアクティブコアがある。ロジックの置き場所で選ぶ。

<wcs-state>

HTML-first — this page

  • State declared in a tag; bindings are path strings in data-wcs
  • Mustache syntax, 48 filters, for / if directives
  • SSR + hydration, in-page DevTools integration
  • Best when the app is written in HTML
@wcstack/signals

JS-first

  • signal / computed / effect in plain modules
  • Fine-grained h() DOM, keyed For / Index
  • ≈3.1 KB core, TC39-shaped API
  • Best when logic lives in TypeScript

The contract: paths #

A <wcs-state> element manages reactive state. data-wcs attributes bind DOM to paths like user.name or cart.items.*.subtotal. The component's JavaScript never references the DOM; the HTML alone describes every data dependency.

<wcs-state>が状態を管理し、data-wcs属性がDOMをパスに結びつける。JavaScriptはDOMを一切参照しない。

The update rule

Reactivity is driven by path assignment. Assign to a path via this["path.to.value"] or a top-level property — deep in-place mutation is not detected.

更新は「パスへの代入」で検出される。オブジェクトの深い直接変更は検出されない。

state.jsUpdate rule
this.count = 10;                    // ✓ detected
this["user.name"] = "Bob";          // ✓ detected
this.user.name = "Bob";             // ✗ NOT detected — no path assignment

// Arrays: non-destructive reassignment
this.items = this.items.concat({ id: 4 });   // ✓
this.items = this.items.toSpliced(0, 1);     // ✓
this.items.push({ id: 4 });                  // ✗ in-place mutation not detected

These are not conditional suspicions — the undetected shapes always drop the update. As of v1.31.0 the linter treats all three (wcs/nested-assign, wcs/array-mutation, wcs/array-index-assign) as errors, so wcs-validate fails a build containing any. And a bound path that provably does not resolve (user.nmae) warns once at binding time with wcs/binding-path-missing and a did-you-mean — the check under-approximates, so absence of a warning proves nothing.

これらは条件つきの疑いではない — 検出されない形は常に更新を落とす。v1.31.0からlinterは3つすべて(wcs/nested-assign・wcs/array-mutation・wcs/array-index-assign)をerrorとして扱い、1つでも含むビルドはwcs-validateで落ちる。また、確実に解決しないバインド済みパス(user.nmae)はバインド時にwcs/binding-path-missingとdid-you-meanつきで一度警告される — 検査は過小近似なので、警告がないことは何の証明にもならない。

v4.0.0: writing a top-level key the state does not have creates it (this.later = 5; 3.x failed the write), while reading one throws [wcs/binding-path-missing] Path "later" does not exist on the state tree. (#301) — so declare every key you bind, null included, in the initial state. A deeper path that does not exist (user.nickname) reads as undefined, and the did-you-mean warning comes from the diagnostics feature, which the full entries include.

v4.0.0: stateに無いトップレベルのキーへの書き込みはそれを作る(this.later = 5。3.xは書き込みを失敗させていた)。一方でその読みは[wcs/binding-path-missing] Path "later" does not exist on the state tree.(#301)をthrowする — だからバインドするキーは、nullも含めてすべて初期のstateで宣言すること。存在しない深いパス(user.nickname)の読みはundefinedで、did-you-meanの警告は完全版のエントリが載せるdiagnostics機能が出す。

Defining state #

State sources (resolution order)

  1. state="id" → a <script type="application/json" id> element
  2. src="*.json" or src="*.js" → external file
  3. json='{ }' → inline JSON attribute
  4. Inner <script type="module"> → export default
  5. setInitialState() → programmatic API

v3.5.0: the browser evaluates an inner <script type="module"> itself as well — being inside <wcs-state> does not stop it. Its export goes nowhere, so the state is unaffected, but its top-level code runs twice, once by the browser and once by state: keep requests, logging and assignments to globals out of the top level. Under a Content-Security-Policy, state imports that script through a blob: URL, and a module’s import() inherits the nonce of the <script> that loaded it, so the page nonce on the <script> that loads state covers it (checked on Chromium, Firefox and WebKit — the docs used to say a nonce could not help). script-src blob: is needed only where no nonce can be issued, and src="./state.js" needs no extra directive. Unless the inner script carries the nonce too, the browser’s own run of it is refused with one console violation, and state still loads. A CSP block of that import is now named as one on Firefox too, which fires the violation a task after the failed import. Details: docs/csp.md.

v3.5.0: 内側の<script type="module">はブラウザ自身も評価する — <wcs-state>の中にあってもそれは止まらない。そのexportはどこにも届かないのでstateには影響しないが、トップレベルのコードは2回走る。ブラウザが1回、stateが1回だ: リクエスト・ログ・グローバルへの代入はトップレベルに置かないこと。Content-Security-Policyの下では、stateはそのスクリプトをblob:のURLでimportし、モジュールのimport()はそれを読み込んだ<script>のnonceを受け継ぐので、stateを読み込む<script>にページのnonceを付ければそれで通る(Chromium・Firefox・WebKitで確認済み — 文書はnonceでは助けにならないと言っていた)。script-src blob:が要るのはnonceを発行できない場合だけで、src="./state.js"なら追加のディレクティブは要らない。内側のスクリプトにもnonceを付けない限り、ブラウザ自身によるその実行はコンソールの違反1件とともに拒まれ、stateは変わらず読み込まれる。そのimportがCSPで止められたことは、失敗したimportの1タスク後に違反を発火させるFirefoxでも、いまはCSPとして名指しされる。詳細: docs/csp.md。

v4.0.0: a source that cannot be read fails the element’s initialization instead of starting an empty state. state="id" reads only a <script type="application/json"> of that id — in the element’s own root first (a shadow root), then in the document — and without one fails with #16; a src="*.json" that cannot be fetched fails with #13 and the HTTP status, and JSON that does not parse and a module that throws fail initialization too (see Lifecycle hooks for how a failure is reported). An empty JSON script is {}. A root <wcs-state> taken out of its root while its state loads mounts nothing there and starts again where it is connected next: a state given by setInitialState() is kept for that, but a state / src / json / inline source is read again, an inline module’s top-level code included.

v4.0.0: 読めないソースは、空のstateで始める代わりに要素の初期化を失敗させる。state="id"が読むのはそのidの<script type="application/json">だけで — 要素自身のルート(shadow root)を先に、次に文書を探す — 無ければ#16で失敗する。取得できないsrc="*.json"はHTTPステータスとともに#13で失敗し、解析できないJSONやthrowするモジュールも初期化を失敗させる(失敗の報告のされ方はライフサイクルフックを参照)。空のJSONスクリプトは{}だ。stateの読み込み中にルートから取り出されたルートの<wcs-state>は、そこには何もマウントせず、次に接続された場所で始め直す: setInitialState()で渡したstateはそのために保たれるが、state / src / json / インラインのソースはもう一度読まれる。インラインのモジュールのトップレベルのコードも同じだ。

Mounting additional state (mount)

There is one state tree per root. To split state across modules, mount a volume: its data is grafted onto the root tree at the mount path, and bindings read it by prefix. This is mount /dev/sdb1 /mnt/data, not a second namespace. The root <wcs-state> is required (it may be empty), load order does not matter — a volume connected before the root is grafted when the root’s engine is created, before the page is bound, and one connected while the root is out of the page is grafted when it is put back — and mount paths are static (*, $, #, @ and whitespace are rejected). A volume holds data, getters, setters and methods, and may declare $connectedCallback / $disconnectedCallback, all relative to its mount point; 4.0 makes its methods reachable by path (onclick: cart.checkout, this["cart.checkout"]() from the root) and refuses a volume that declares what reacts to the whole tree (below).

stateの木はルートごとに1本。モジュールに分けるときはボリュームをマウントする。データはルートの木のマウントパスに接ぎ木され、バインディングは接頭辞付きのパスで読む。第二の名前空間ではなくmount /dev/sdb1 /mnt/dataである。ルートの<wcs-state>は必須(空でよい)で、ロード順は問わない — ルートより先に接続されたボリュームは、ルートのエンジンが作られるとき、ページがバインドされる前に接ぎ木され、ルートがページの外にある間に接続されたボリュームは、ルートが戻されたときに接ぎ木される — マウントパスは静的(* $ # @と空白は不可)。ボリュームはデータ・getter・setter・メソッドを持ち、$connectedCallback / $disconnectedCallbackを宣言でき、どれもマウント点からの相対だ。4.0はそのメソッドをパスで届くようにし(onclick: cart.checkout、ルートからはthis["cart.checkout"]())、木全体に反応するものを宣言したボリュームを拒む(後述)。

Migrating from v1 named state. name= and path@name were removed in v2: name="cart" becomes mount="cart", total@cart becomes cart.total, and @default simply drops. The runtime fails fast on name= and treats @ in a path as a parse error, both printing the replacement, and wcs/named-state-deprecated lists every remaining site as a lint error. One volume caveat: $stream raises on a volume, and $commandTokens / $eventTokens / $on belong on the root — those are the only declarations that are not a plain rename.

v1のnamed stateからの移行。 name=とpath@nameはv2で削除された。name="cart"はmount="cart"に、total@cartはcart.totalに、@defaultは単に外す。ランタイムはname=で即座に失敗し、パス中の@はparse errorになり、どちらも置き換え先を表示する。残った箇所はwcs/named-state-deprecatedがlintのerrorとして列挙する。ボリュームでの注意は1つ — $streamはボリュームでは不可、$commandTokens / $eventTokens / $onはルートに置く。単純なリネームで済まないのはこの4つだけ。

v2.5.0: a volume that settles without grafting releases its mount slot — it failed to load, its root failed and orphaned it, or it was detached while still loading or waiting for that root. Until now the slot stayed reserved for as long as the root node lived, so a replacement element on the same path was rejected with Volume slot "…" is already mounted on this tree. — an error nothing awaiting the page ever saw — and reloading was the only recovery. A released slot is taken back when the element is re-attached to the same root, or otherwise just before it grafts; if another volume took it meanwhile, that is reported and the graft is skipped. A grafted volume keeps its slot even while detached, a release only removes that element’s own reservation (so removing a dead volume never frees a slot another one holds), and reads under a released path still resolve to undefined. In the same release, setInitialState() on a loaded volume element throws: the graft copies a volume’s data into the root tree once, so re-setting the element only ever changed that element’s own reads. Write the paths under the mount path on the root instead.

v2.5.0: 接ぎ木せずに決着したボリュームはマウントスロットを解放する — 読み込みに失敗した、ルートが失敗して孤立した、読み込み中やルート待ちのまま外された、のいずれでも。これまではルートノードが生きているかぎりスロットは予約されたままで、同じパスへの代わりの要素はVolume slot "…" is already mounted on this tree.で拒否された — ページを待っている誰にも見えないエラーだ — 復旧はリロードしかなかった。解放されたスロットは、同じルートへ再接続されたとき、あるいは接ぎ木の直前に取り戻される。その間に別のボリュームが取っていれば、それが報告され接ぎ木は行われない。接ぎ木済みのボリュームは外れていてもスロットを保ち、解放はその要素自身の予約だけを外し(死んだボリュームを取り除いても他のボリュームのスロットは空かない)、解放されたパスの下の読みは従来どおりundefinedになる。同じリリースで、読み込み済みのボリューム要素へのsetInitialState()はthrowする: 接ぎ木はボリュームのデータをルートの木へ一度だけコピーするので、要素の再セットはその要素自身の読みしか変えなかった。代わりにルート側でマウントパス配下のパスに書くこと。

Injecting root paths into a volume (v3.1.0 – v3.5; refused in 4.0). 4.0 takes no injections: any data-wcs on a <wcs-state mount> counts as one, and the volume is not grafted (see v4.0.0 below). Read the root path in a getter on the root state instead — get cartTotalWithTax() { return this["cart.subtotal"] * (1 + this["settings.taxRate"]); } — and wrap the volume element in an element of your own to bind something to it. The rest of this subsection describes 3.1 to 3.5. When a volume’s code needs a path outside its own subtree, write the injection on the volume element’s data-wcs, in the same form as a component’s partial mount (until 3.1 such a data-wcs failed to apply as a write to a missing state property):

ボリュームへのルートのパスの注入(v3.1.0 – v3.5。4.0では拒まれる)。 4.0は注入を受けない: <wcs-state mount>のdata-wcsはどれも注入とみなされ、そのボリュームは接ぎ木されない(下のv4.0.0を参照)。代わりにルートのパスはルートのstateのgetterで読み — get cartTotalWithTax() { return this["cart.subtotal"] * (1 + this["settings.taxRate"]); } — ボリューム要素そのものに何かをバインドしたいなら、自分の要素で包むこと。この小節の残りは3.1から3.5の説明だ。ボリュームのコードが自分の部分木の外のパスを要るときは、ボリューム要素のdata-wcsに、コンポーネントの部分マウントと同じ形で注入を書く(3.1より前、そうしたdata-wcsは存在しないstateプロパティへの書き込みとして適用に失敗していた):

index.htmlVolume injection (3.1 – 3.5)
<wcs-state mount="cart" src="./cart.js" data-wcs="state.taxRate: settings.taxRate"></wcs-state>

Inside cart.js — getters, methods, $watch, $listKeys and the lifecycle callbacks — this.taxRate reads and writes the root’s settings.taxRate. The read records a dependency, so get total() re-evaluates when settings.taxRate changes; $watch: { taxRate() {…} } fires on it, and $renderedCallback receives that update under the inner name taxRate. The injected name exists only inside the volume’s code: the page keeps reading settings.taxRate, and the tree has no cart.taxRate.

cart.jsの中 — getter・メソッド・$watch・$listKeys・ライフサイクル — では、this.taxRateがルートのsettings.taxRateを読み書きする。読みは依存を記録するので、settings.taxRateが変わればget total()は再評価され、$watch: { taxRate() {…} }はそれで発火し、$renderedCallbackはその更新を内側の名前taxRateで受け取る。注入された名前が存在するのはボリュームのコードの中だけで、ページはsettings.taxRateを読み続け、木にcart.taxRateは無い。

  • One key at a time. The left side is a single state.<key>; state: … cannot move the whole volume — change mount for that.
  • The injection wins over the volume’s own key. A data key of the same name (taxRate: 0) is not grafted. An accessor or method of the same name would make this.taxRate ambiguous, so that volume reports an error and does not graft.
  • #ro. With state.taxRate#ro: settings.taxRate the value can be read but not written: an assignment, $setAll or a writing $resolve from the volume’s code throws [wcs/mount-readonly]. The root itself can still write the path.
  • Static paths only. The right side cannot contain a wildcard or start with $ — a volume has no loop context — and takes no filters; derive the value in a getter. A malformed injection is reported as [wcs/mount-path-invalid] before the volume loads.

規則は4つ。1つずつ: 左辺はstate.<key>1つで、state: …でボリューム全体を動かすことはできない — それにはmountを変える。注入はボリューム自身のキーに勝つ: 同名のデータキー(taxRate: 0)は接ぎ木されない。同名のアクセサやメソッドはthis.taxRateを曖昧にするので、そのボリュームはエラーを報告して接ぎ木しない。#ro: state.taxRate#ro: settings.taxRateなら値は読めるが書けない — ボリュームのコードからの代入・$setAll・書き込みの$resolveは[wcs/mount-readonly]をthrowする。ルート自身は今もそのパスに書ける。静的なパスだけ: 右辺はワイルドカードを含めず$で始められず — ボリュームにはループの文脈が無い — フィルタも取らない。値はgetterで導くこと。形の崩れた注入は、ボリュームの読み込み前に[wcs/mount-path-invalid]として報告される。

v3.3.0: the state namespace on a <wcs-state> without mount= reports [wcs/mount-path-invalid] — one key is told to move to a volume element, a bare state: that the name is reserved — instead of failing later as a write to a missing property, and .state: / .state.<key>: are rejected with [wcs/binding-syntax], because on a volume the dotted form was silently read as an injection. With several injections (state.a: settings; state.b: settings.tax), $renderedCallback names an updated path by the longest match, as reads do, instead of by the order they were written in. A volume written as a class grafts its prototype accessors — class Cart { get total() {…} } used to lose total without a word — and this.$x = … in a volume no longer creates a cart.$x key in the tree.

v3.3.0: mount=の無い<wcs-state>に書いたstate名前空間は、後で存在しないプロパティへの書き込みとして失敗する代わりに[wcs/mount-path-invalid]を報告する — キー1つならボリューム要素へ移すよう、素のstate:ならその名前が予約されていると告げる。.state: / .state.<key>:は[wcs/binding-syntax]で拒まれる。ボリューム上ではドット付きの形が黙って注入として読まれていたからだ。注入が複数あるとき(state.a: settings; state.b: settings.tax)、$renderedCallbackは更新されたパスを、書いた順ではなく読みと同じ最長一致で名付ける。クラスで書いたボリュームはプロトタイプのアクセサを接ぎ木する — class Cart { get total() {…} }は黙ってtotalを失っていた — そしてボリューム内のthis.$x = …が木にcart.$xというキーを作ることはもう無い。

v3.5.0: 4.0 will not graft a volume that injects root paths, or that declares $watch, $listKeys, $renderedCallback, $behavior or $features — it reports the volume with console.error instead. All of them still work in 3.x, and 3.5 names each one once with [wcs/v4-migration]. To be ready, read the root path in a getter on the root state, and move those declarations to the root state with absolute paths (see Migrating from 3.x).

v3.5.0: 4.0は、ルートのパスを注入するボリューム、あるいは$watch・$listKeys・$renderedCallback・$behavior・$featuresを宣言するボリュームを接ぎ木せず、代わりにそのボリュームをconsole.errorで報告する。3.xではどれも今も動き、3.5はそれぞれを[wcs/v4-migration]で一度ずつ名指しする。備えるには、ルートのパスはルートのstateのgetterで読み、それらの宣言は絶対パスにしてルートのstateへ移す(3.xからの移行を参照)。

v4.0.0: a volume no longer runs the declarations that react to the whole tree. One that declares $watch, $listKeys, $renderedCallback, $behavior or $features (or $stream, $recursion and the removed $scan, $streams, $updatedCallback), or that carries a data-wcs of any kind, is not grafted: console.error names the element and the reason — [@wcstack/state] <wcs-state mount="cart"> $watch is not run in a volume — declare it on the root state. — and its connectedCallbackPromise still resolves. Other refusals say why as well: will not graft: the root state already has "cart"., will not graft: its component is wired to its host. (3.x left that one pending), and will not graft: the root state failed to initialize. for the volumes of a root that failed. A changed mount attribute is ignored without a message — remove the element and add a new one. The 4.0 lint reports these declarations as wcs/volume-declaration.

v4.0.0: ボリュームは、木全体に反応する宣言をもう動かさない。$watch・$listKeys・$renderedCallback・$behavior・$features(あるいは$stream・$recursionと、取り除かれた$scan・$streams・$updatedCallback)を宣言するボリューム、どんな種類であれdata-wcsを持つボリュームは接ぎ木されない: console.errorが要素と理由を名指しし — [@wcstack/state] <wcs-state mount="cart"> $watch is not run in a volume — declare it on the root state. — そのconnectedCallbackPromiseは変わらずresolveする。それらはルートのstateに完全なパスで宣言する: ルートのハンドラの中のthisはルートで($watch: { "cart.total"(cur) { … } })、ルートの$renderedCallback(paths)はルートから書いたパス(cart.items.*.name)を受け取るので、接頭辞で絞り込む。ボリュームの$commandTokens・$eventTokens・$on・$errorCallbackはconsole.warnとともに動かない。ほかの拒否も理由を告げる: will not graft: the root state already has "cart".、will not graft: its component is wired to its host.(3.xはこれを保留のままにしていた)、そして失敗したルートのボリュームにはwill not graft: the root state failed to initialize.。変更したmount属性はメッセージ無しに無視される — 要素を取り除いて新しいものを加えること。4.0のlintはこれらの宣言をwcs/volume-declarationとして報告する。

Path getters #

Computed properties are defined with dot-path string keys, flat at the top level, regardless of how deep the data nests. The wildcard * abstracts the loop index away.

state.jsVirtual properties
export default {
  users: [
    { id: 1, firstName: "Alice", lastName: "Smith" },
    { id: 2, firstName: "Bob",   lastName: "Jones" }
  ],
  get "users.*.fullName"() {
    return this["users.*.firstName"] + " " + this["users.*.lastName"];
  },
  // Path setters — split a write back into its parts
  set "users.*.fullName"(value) {
    const [first, ...rest] = value.split(" ");
    this["users.*.firstName"] = first;
    this["users.*.lastName"]  = rest.join(" ");
  },
  // Top-level aggregation over a wildcard
  get totalUsers() {
    return this.$getAll("users.*.id", []).length;
  }
};

Recursive paths ($recursion)

A path burns its depth into the string, but a tree’s depth belongs to the data. v2.3.0: declare where the shape repeats — an anchor and the sub-path that descends one level — and ** stands for “however deep this is”. One getter then covers every depth, and each depth’s accessor is materialized the first time it is read.

パスは深さを文字列に焼き付けるが、木の深さはデータに属する。v2.3.0: 形が繰り返される場所 — アンカーと1段降りる部分パス — を宣言すれば、**が「ここが何段であろうと」を表す。getter 1つがすべての深さを覆い、各深さのアクセサは最初に読まれたときに実体化される。

state.jsOne getter, every depth
export default {
  $recursion: { "nodes.*": "children.*" },   // anchor → repeating sub-path

  nodes: [ { value: 1, children: [ { value: 10, children: [] } ] } ],

  // `**` is bound to the depth being evaluated; the index-omitted
  // $getAll reads exactly the direct children of that node.
  get "nodes.**.total"() {
    return this["nodes.**.value"]
         + this.$getAll("nodes.**.children.*.total").reduce((a, b) => a + b, 0);
  },
  // `[]` unions every depth — depth-first, pre-order, ascending index
  get treeTotal() {
    return this.$getAll("nodes.**.value", []).reduce((a, b) => a + b, 0);
  },
  clearSelection() {
    this.$setAll("nodes.**.selected", [], false);   // broadcast to every node
  }
};

Bound or unioned is decided by context, the same split * has between “the current row” and “every row”: a getter key and reads inside it are bound to the depth being evaluated, $getAll with indexes omitted stays at that depth, and $getAll(path, []) unions every depth. The omitted form is what makes an aggregate fold its own subtree exactly once; unioning an aggregate from outside double-counts, and that is not decidable from the path string, so no diagnostic claims to catch it. Bound reads need a depth, so they resolve only inside a recursive getter, a row getter under the anchor, or a handler bound to such a row — elsewhere it is wcs/recursion-context.

束縛か連結かは文脈が決める。*の「現在の行」と「すべての行」と同じ対比だ: getterのキーとその内側の読みは評価中の深さに束縛され、インデックスを省いた$getAllはその深さに留まり、$getAll(path, [])は全深さを連結する。集計が自分の部分木をちょうど1回だけ畳み込むのは省略形のおかげ。外から集計値を連結すると二重計上になるが、これはパス文字列からは決定できないので、捕まえると称する診断は無い。束縛形の読みは深さを必要とするため、再帰getter・アンカー配下の行getter・その行に束縛されたハンドラの中でのみ解決する。それ以外ではwcs/recursion-context。

** is authoring notation only — PathInfo, the dependency graph, $1…$n, $resolve and the list diff only ever see ordinary fixed-arity paths. What cannot be expressed that way is refused rather than reinterpreted, under the wcs/recursion-* codes the linter shares: a recursive getter is read-only (write what it derives from), a broadcast at the structure itself is refused, ** in markup / $watch / $listKeys / $resolve is wcs/recursion-unsupported, and this version takes exactly one self-recursive anchor per state, a tree as input (a shared child array or a cycle is named) and 128 wildcard levels. $recursion and ** getters are root-only. Rendering a tree stays with a self-referential component: ** cannot appear in markup, and inside each scope only one level of path is ever used.

**は記述上の記法にすぎない — PathInfo・依存グラフ・$1…$n・$resolve・リスト差分が見るのは、常に固定アリティの普通のパスだ。そう表現できないものは再解釈されずに拒まれる。コードはlinterと共通のwcs/recursion-*: 再帰getterは読み取り専用(導出元に書くこと)、構造そのものへのブロードキャストは拒否、マークアップ・$watch・$listKeys・$resolve中の**はwcs/recursion-unsupported。このバージョンが受け付けるのはstateごとに自己再帰アンカー1つ、入力は木(子配列の共有や循環は名指しされる)、ワイルドカードは128段まで。$recursionと**getterはルート専用。木の描画は従来どおり自己参照コンポーネントが担う: **はマークアップに書けず、各スコープの中で使うパスは常に1段だけだ。

Getters must be pure with respect to state

A getter’s cache is invalidated only through the dependency graph, and the graph records only what was read through this. A getter reading Date.now(), the DOM, or a module variable therefore keeps its first value forever — with no warning. Read only through this; when an untracked input must participate, put it into state and assign to it, or use $dependOn / $postUpdate / $untracked. Getters that throw are not swallowed: the exception surfaces where the getter was evaluated.

getterのキャッシュは依存グラフ経由でのみ無効化され、グラフはthis越しの読み取りしか記録しない。Date.now()・DOM・モジュール変数を読むgetterは、警告なしに最初の値を永遠に保持する。読むのはthis越しだけにする。追跡外の入力を関与させたいときは、stateに入れて代入するか、$dependOn / $postUpdate / $untrackedを使う。throwするgetterは握りつぶされず、評価された場所で例外が表面化する。

Keyed selection ($eq / $eqPath / $eqIndex)

A row getter that answers “is this row the selected one?” is where dependency tracking scales worst: get "items.*.selected"() { return this.$1 === this.selectedIndex; } makes every row depend on selectedIndex, so one click re-evaluates 10,000 getters. v2.6.0: the keyed forms subscribe each row under its own key instead, and a write to the path re-evaluates only the row that was selected and the row that becomes selected — selecting one of 10,000 rows goes from 20 ms to 0.2 ms.

「この行は選択中か」を答える行getterは、依存追跡が最も効きにくい形だ: get "items.*.selected"() { return this.$1 === this.selectedIndex; }は全行をselectedIndexに依存させるので、1クリックで1万個のgetterが再評価される。v2.6.0: 鍵付きの形は各行をその行自身の鍵の下に購読させ、パスへの書き込みで再評価するのは選択されていた行と選択される行だけにする — 1万行から1行を選ぶ操作は20 msから0.2 msになった。

What reaches the rows. On 2.6.0 the first three could leave a row selected, or never select it, without an error; v2.6.1 closed all three.

  • A write to path — of any value, objects included (this.selected = row with $eq("selected", this["items.*"])): the row that was selected and the row that becomes selected. The rows are keyed by the value they last saw, so an object write, or any write with config.sameValueGuard off, finds the previous row too.
  • A write to an object above path — this.sel = { id: 2 } for $eq("sel.id", …): the same two rows, keyed by the value path had under the old object and has under the new one.
  • A path that is a getter, or sits under one ($eq("current.id", …) with get current()): its value changes without a write to it, so the calls fall back to an ordinary tracked read. The selection stays correct, but a change re-evaluates every row, as without the keyed form — point path at the written state (selectedId) to keep the two-row cost.
  • No type conversion. Keys compare as Map keys (Object.is, with +0 / -0 and NaN / NaN equal), so "2" does not match the id 2. An <input> or <select> writes strings: convert on the way in (value|number: selectedId) or keep the ids as strings.

行に届くもの。2.6.0では最初の3つがエラーなしに行を選択したまま残すか、一度も選択しないことがあった — v2.6.1で3つとも塞がれた。pathへの書き込みは、オブジェクトを含むどんな値でも($eq("selected", this["items.*"])でthis.selected = row)選択されていた行と選択される行に届く。行は最後に見た値で鍵付けされるので、オブジェクトの書き込みでも、config.sameValueGuardを切った書き込みでも前の行が見つかる。pathの上のオブジェクトへの書き込み($eq("sel.id", …)に対するthis.sel = { id: 2 })も同じ2行に届き、鍵は古いオブジェクトでのpathの値と新しいオブジェクトでの値だ。getterであるpath、またはgetterの下にあるpath(get current()がある$eq("current.id", …))は、書き込み無しに値が変わるので、普通の追跡付きの読みに戻る。選択は正しいままだが、変化のたびに鍵付きの形を使わないときと同じく全行が再評価される — 2行分のコストを保つには、pathを書き込む先のstate(selectedId)に向ける。型変換はしない: 鍵はMapの鍵として(Object.is、ただし+0 / -0とNaN同士は等しい)比較されるので、"2"はid 2に一致しない。<input>や<select>は文字列を書くので、入口で変換する(value|number: selectedId)か、idを文字列のまま持つ。

The calls subscribe only while a getter is being evaluated — from a method or a handler $eq / $eqPath just return the comparison — and $eqIndex takes its key from a list row, so outside one it throws. A row’s subscription is dropped when the list diff removes the row, and a key no row holds any more leaves the ledger with it, so a removed row object is not retained (v2.6.1). $eqPath reads the key without a dependency, so a row whose key changes in place is not re-evaluated by that change: use it for identities that do not change, and $eq with a tracked read when the key itself is live. 3.0: the State pane of @wcstack/devtools lists the subscriptions per path under Keyed selection and marks a path that fell back to a tracked read with a tracked badge — the one case above that costs every row.

購読が張られるのはgetterの評価中だけで — メソッドやハンドラからの$eq / $eqPathは比較結果を返すだけ — $eqIndexは鍵をリスト行から取るので、行の外ではthrowする。行の購読はリスト差分がその行を外した時点で落ち、どの行も持たなくなった鍵も台帳から一緒に消えるので、取り除いた行オブジェクトが保持され続けることはない(v2.6.1)。$eqPathは鍵を依存なしで読むので、鍵がその場で書き換わった行はその変更では再評価されない: 変わらない同一性(id)に使い、鍵そのものが動くなら追跡付きの読みと$eqを組み合わせる。3.0: @wcstack/devtoolsのStateペインはKeyed selectionの下にパスごとの購読を並べ、追跡付きの読みに戻ったパスにtrackedバッジを付ける — 上のうち全行ぶんのコストがかかる唯一の場合だ。

v3.3.0: inside a mounted component or a volume, $eq / $eqPath / $eqIndex resolve against that scope’s own paths ($eqPath translates both of its paths). They used to read the root’s, so this.$eq("selectedId", 2) inside <wcs-state mount="cart"> compared against the root’s selectedId — a silent false, or a throw naming a path the author never wrote. A getter derived from a keyed getter (get label() { return this.picked; } over get picked() { return this.$eq(…); }) no longer keeps its old value, also after a list diff re-keys $eqIndex rows, and $postUpdate after an in-place mutation notifies the keyed rows. A selection change at 10,000 rows still re-evaluates about two getters. v3.3.0: マウントされたコンポーネントやボリュームの中では、$eq / $eqPath / $eqIndexはそのスコープ自身のパスで解決される($eqPathは2つのパスの両方を翻訳する)。以前はルートのパスを読んでいたので、<wcs-state mount="cart">の中のthis.$eq("selectedId", 2)はルートのselectedIdと比べていた — 黙ってfalseを返すか、作者が書いてもいないパスを名指ししてthrowした。鍵付きgetterから導いたgetter(get picked() { return this.$eq(…); }の上のget label() { return this.picked; })はもう古い値を保たず、リスト差分が$eqIndexの行の鍵を付け替えた後も同じだ。その場の変更の後の$postUpdateも鍵付きの行に届く。1万行での選択の変更が再評価するgetterは今も約2個だ。ネストしたリストの親の行を退けると子の購読も落ちるので、DevToolsの件数がページ上の行数を超えて育つことはもう無い。

v3.4.0: a path with a numeric index ($eq("items.0.v", "b")) falls back to a tracked read, as a getter path does. A write reports the index as a wildcard (items.*.v, items.*), so a keyed subscription under the spelled path never heard it: the getter kept its first value through this["items.0.v"] = "b" and this["items.0"] = { v: "b" } and followed only a replacement of the list. It now follows all three, at the cost of re-evaluating on a write to any row’s v, and DevTools marks the path tracked. A $eqIndex that falls back this way records the row index as read, so a row that only moves (a reorder, an insert above it) is re-evaluated. 4.0: $eq / $eqPath key only paths outside lists, so a wildcard path ($eq("items.*.v", …)) falls back the same way, and follows a write to that row’s v, a replacement of the element and of the list.

v3.4.0: 数値インデックスを持つpath($eq("items.0.v", "b"))は、getterのパスと同じく追跡付きの読みに戻る。書き込みはインデックスをワイルドカードとして報告する(items.*.v、items.*)ので、綴ったとおりのパスの下の鍵付きの購読には届かなかった: getterはthis["items.0.v"] = "b"やthis["items.0"] = { v: "b" }を経ても最初の値を保ち、追従したのはリストの置き換えだけだった。いまは3つすべてに追従し、その代わりにどの行のvへの書き込みでも再評価され、DevToolsはそのパスにtrackedを付ける。こうして戻った$eqIndexは行のインデックスを読んだものとして記録するので、移動しただけの行(並べ替え、上への挿入)も再評価される。4.0: $eq / $eqPathが鍵付けするのはリストの外のパスだけなので、ワイルドカードのpath($eq("items.*.v", …))も同じように戻り、その行のvへの書き込み、要素の置き換え、リストの置き換えに追従する。

Demand roots — what makes a getter run

Getters are lazy, and exactly three things create demand: a live DOM binding (demand disappears with the element), a $watch declaration (headless), and a $stream args function. $renderedCallback is not a root — it reports what the bindings did. Logic that must not depend on what is rendered belongs on $watch or args; $renderedCallback testing a path nothing binds is detected statically as wcs/updated-callback-unbound (v1.31.0).

getterは遅延評価で、需要を生むものはちょうど3つ。ライブなDOMバインディング(要素が消えれば需要も消える)、$watch宣言(ヘッドレス)、$streamのargs関数。$renderedCallbackはrootではない — バインディングが行ったことを報告するだけだ。描画に依存してはならないロジックは$watchかargsに置く。何もバインドしていないパスを$renderedCallbackで調べる形はwcs/updated-callback-unboundとして静的に検出される(v1.31.0)。

One numeric index (v3.4.0). A binding path with exactly one numeric index — textContent: items.0.v, {{ users.1.name }}, a row getter {{ users.0.fullName }} — means what this["users.0.name"] means in code: whatever row is at index 0 now. Through 3.3 it was a plain key path: it kept its first value through an index-path write, a for: row input, an element replacement or a reorder, followed only a replacement of the whole list, and a row getter spelled that way rendered empty with wcs/binding-path-missing. It is now read like a getter over the row, through a non-enumerable accessor on the state object (Object.keys, JSON.stringify and the SSR snapshot do not see it), with or without a for:. Like a getter it is re-evaluated when any row of the list is written, and a $watch on "items.0.v" can fire with an unchanged value; in happy-dom one batch of 1,000 index-path writes to a 1,000-row list took 4–5 ms with no such binding, about 87 ms with 100 and 180–220 ms with 300. Three cases keep the 3.3 reading: two or more numeric indexes (groups.0.items.1.v), a state that cannot be extended (Object.freeze / seal / preventExtensions), and a key the state declares under that very name. What the page walk binds (4.0)

When a <wcs-state> binds its root — the document, a shadow root, or a Light DOM component’s host — it walks the markup once. A value is never markup: what a binding puts into the page is never read as bindings. 4.0 adds rules 3.x did not have:

  • The children of an element whose content a binding sets (textContent:, text:, innerText:, innerHTML:, html:) are not bound, at page level or inside templates — also when #init=element or #init=none leaves the children you wrote in place. Put markup that needs bindings in a separate element.
  • The content of <noscript> and <iframe> is not walked, as <script> and <style> were not; the element’s own data-wcs (srcdoc:, attr.src:) still binds.
  • At page level an element’s children are bound before the element’s own bindings, so a custom element receives its first property writes after its children are bound, and $errorCallback receives failures children first. Inside templates the order is document order.
  • for: rows and if: branches are clones of their templates without the data-wcs attribute (3.x kept it, with the paths expanded), so a CSS rule or a test selector on [data-wcs…] no longer matches those elements — use a class or a data-* attribute of your own.
  • Inside a for: / if: template, outerHTML: / outerText: fail initialization with [wcs/template-syntax] #203 — a row keeps its nodes by position, and 3.x applied the replacement once. Bind innerHTML: on a wrapper element instead.

<wcs-state>は自分のルート — 文書、shadow root、あるいはLight DOMのコンポーネントのホスト — をバインドするとき、マークアップを一度だけ歩く。値は決してマークアップではない: バインディングがページに置いたものがバインディングとして読まれることは無い。4.0は3.xに無かった規則を加える。内容を設定するバインディング(textContent:・text:・innerText:・innerHTML:・html:)を持つ要素の子は、ページ直下でもテンプレートの中でもバインドされない — #init=elementや#init=noneが書いた子をそのまま残すときも同じだ。バインディングの要るマークアップは別の要素に置くこと。<noscript>と<iframe>の中身は、<script>や<style>と同じく歩かれない。要素自身のdata-wcs(srcdoc:・attr.src:)は今もバインドされる。ページ直下では要素の子が要素自身のバインディングより先にバインドされるので、カスタム要素が最初のプロパティの書き込みを受け取るのは子がバインドされた後で、$errorCallbackは子の失敗から先に受け取る。テンプレートの中では文書順だ。for:の行とif:の枝はテンプレートのdata-wcs属性を持たない複製なので(3.xはパスを展開して残していた)、[data-wcs…]に対するCSSのルールやテストのセレクタはもうその要素に当たらない — クラスや自分のdata-*属性を使うこと。for: / if:のテンプレートの中のouterHTML: / outerText:は[wcs/template-syntax] #203で初期化を失敗させる — 行はノードを位置で持ち、3.xは置き換えを一度だけ適用していた。代わりにラッパー要素にinnerHTML:をバインドすること。

v2.5.0: swapping or replacing rows by writing elements — this.$resolve("items.*", [0], b), this["items.0"] = c — keeps the page, the reads and the writes on the same rows. A completed swap is re-rendered as a replacement of the order before the writes, so the row blocks move with their values, and a row’s $1 and the DOM state the bindings do not own (text typed into an unbound input) move with them. Writing a value that was not in the list replaces that row in place: the block stays where it is, an input being edited in it keeps focus, and the row’s getters show the new row. Equal primitives cannot be told apart, so writes that end in a reordering of the same values count as a swap. The completed swap is queued render-only, so $watch fires for neither items nor items.* on a row that merely moved. $listKeys — identity for refetched rows

The exception, addressed in v1.26.0, is data that arrives as freshly created objects — fetch(...).json(), a WebSocket snapshot, JSON.parse from storage. Nothing matches by reference, so every row is rebuilt and the DOM state the bindings do not own goes with it: focus, an in-flight IME composition, <details> open state, inner scroll, <canvas> contents. Declare a key and rows are matched across the refresh instead.

例外は毎回新しいオブジェクトとして届くデータ(fetch(...).json()、WebSocketのスナップショット、ストレージからのJSON.parse)。参照が一致しないため全行が作り直され、バインディングが所有していないDOM状態 — フォーカス、変換中のIME入力、<details>の開閉、内側のスクロール、<canvas>の内容 — が失われる。キーを宣言すれば、リフレッシュを越えて行が突き合わせられる。

  • A no-op refresh is free. If nothing changed, no field is written and no DOM work happens.
  • Rows must be plain objects with present, unique keys. Duplicates, missing keys and class instances raise immediately rather than degrading silently.
  • Fields dropped from a row are cleared with null. The stored array is rebuilt from the matched row objects, so this.items !== theArrayYouAssigned afterwards.

Canonical names (v3.2.0). Some names read as the wrong operation or abbreviated away from JavaScript’s, and the chips above show their canonical names: add / sub (were inc / dec), toFixed (fix), upper / lower / capitalize (uc / lc / cap), repeat / reverse (rep / rev), padStart (pad) and nullIfEmpty (null — it turns an empty string into null and passes anything else through). The old names resolve to the same implementation and arity through 3.x and are removed in 4.0; lint and the VS Code extension flag each one as wcs/name-alias (info) with the canonical name, and the runtime starts warning only in the last 3.x minor. Two filters are new: padEnd(n, c?) pads the end (default a space), and coalesce(v) replaces only null / undefined — count|coalesce(0) keeps a real 0, false or "", where defaults(v) replaces every falsy value. Argument literals are typed (3.0). An unquoted true, false, null or number is that value; a quoted argument is a string. done|eq(true) matches true (in 2.x it compared with the string "true" and never matched), eq('true') does not, and eq(null) matches null. A fold accumulates within one run and returns to initial on every restart. An accumulation that has to outlive restarts — an infinite-scroll feed built across page runs — belongs in a plain key written from a $watch on the stream’s value. $scan (v2.4.0) declared exactly that; it warned in 3.5 and is removed in 4.0.

foldは1回の実行の中で蓄積し、再起動のたびにinitialへ戻る。再起動を越えて残るべき蓄積 — ページ実行をまたいで組み立てる無限スクロールのフィード — は、streamの値への$watchから書く普通のキーに置く。$scan(v2.4.0)はまさにそれを宣言するものだった。3.5で警告され、4.0で取り除かれた。

v4.0.0: what a run writes in the same task as its (re)start — a value its source yields at once, its status done / error — continues that run’s chain, for the $watch handlers it fires as for the restarts it causes. A loop through a source that yields at once is therefore cut instead of freezing the page as in 3.x: two streams whose args read each other’s values, or a $watch on a stream’s value that moves what its args reads — one lap of the latter is two links, so it stops after about 16 laps, finite or not, and auto-paging over an in-memory source stops there too (3.x completed it). A value from a later task (a network response, a message, a timer) starts afresh, so a cycle through such values restarts forever — do not build one. On the server streams keep their initial value, and a stream is the temporal feature, which the full entries include.

v4.0.0: 実行が(再)起動と同じタスクの中で書くもの — ソースがすぐに出す値、状態done / error — は、その実行の連鎖を引き継ぐ。それが起こす再起動についても、それが発火させる$watchハンドラについても同じだ。だから、すぐに値を出すソースを経るループは、3.xのようにページを止めずに打ち切られる: 互いの値をargsで読む2つのstream、あるいはstreamの値への$watchがそのargsが読むものを動かす形だ — 後者の1周は2段なので、終わるループでも終わらないループでも約16周で止まり、メモリの上のソースに対する自動ページングもそこで止まる(3.xは最後までやり遂げていた)。後のタスクから来る値(ネットワークの応答、メッセージ、タイマー)は数え直しになるので、そうした値を経る循環は永久に再起動し続ける — 作らないこと。サーバー上のstreamはinitialの値のままで、streamは完全版のエントリが載せるtemporal機能だ。

$scan (removed in 4.0) #

4.0 removes $scan. v2.4.0 added it to declare an accumulation over time — an owner, a firing unit and a reset condition — and 3.5 warned about it. With the diagnostics feature (in @wcstack/state and /auto), a state that declares it fails to load with $scan was removed (use $watch or $on) (#1); on /core without it the key is ignored like any unknown $ key, and a volume that declares it is refused either way. The 4.0 lint reports it as wcs/scan-declaration-invalid (error). features/temporal now serves $watch and $stream only.

4.0は$scanを取り除く。 v2.4.0は時間にわたる蓄積 — 持ち主・発火の単位・リセット条件 — を宣言するためにそれを加え、3.5はそれを警告した。diagnostics機能があれば(@wcstack/stateと/autoは載せている)、それを宣言したstateは$scan was removed (use $watch or $on)(#1)で読み込みに失敗する。それの無い/coreでは、そのキーは未知の$キーと同じく無視され、それを宣言したボリュームはどちらでも拒まれる。4.0のlintはそれをwcs/scan-declaration-invalid(error)として報告する。features/temporalはいま$watchと$streamだけを担う。

Keep the accumulated value as an ordinary key and write it from a handler: a scan with from: "path" becomes a $watch handler on that path, a scan with on: "token" an $on handler for that event token, and resetOn a $watch handler that writes the initial value back.

蓄積した値は普通のキーとして持ち、ハンドラから書く: from: "path"のスキャンはそのパスへの$watchハンドラに、on: "token"のスキャンはそのイベントトークンの$onハンドラに、resetOnは初期値を書き戻す$watchハンドラになる。

state.js3.x only
export default {
  amount: 0,
  room: "lobby",
  $eventTokens: ["message"],
  $scan: {
    total: { from: "amount", initial: 0, fold: (sum, cur) => sum + cur },
    log: { on: "message", initial: [], fold: (log, e) => [...log.slice(-49), e.detail], resetOn: ["room"] },
  },
};
state.js3.5 and 4.0: $watch / $on instead of $scan
export default {
  amount: 0,
  room: "lobby",
  total: 0,                // was $scan.total (from: "amount")
  log: [],                 // was $scan.log (on: "message")
  $eventTokens: ["message"],
  $watch: {
    amount(cur) { this.total = this.total + cur; },
    room() { this.log = []; },   // was resetOn: ["room"]

  $on: {
    message: (state, e) => { state.log = [...state.log.slice(-49), e.detail]; },

};

Like a from scan, a $watch handler sees one settled value per update batch. Two things differ: the value is now plain state that you own (a re-set replaces it like any other key), and a reset happens when the $watch handler runs at the end of the batch, not at the moment of the write. Keep a fold over an infinite source bounded ([...log.slice(-99), x]), and keep an idempotency key in the accumulator where the same page can land twice (a retry, a re-attached element). The 3.x reference for $scan is in the 3.5.4 README.

fromのスキャンと同じく、$watchハンドラが見るのは更新バッチごとに確定した値1つだ。違いは2つある: 値はいまや自分が持つ素のstateであり(再セットは他のキーと同じくそれを置き換える)、リセットは書き込みの瞬間ではなく、バッチの終わりに$watchハンドラが走ったときに起きる。終わりの無いソースに対する畳み込みは上限を設け([...log.slice(-99), x])、同じページが2回着地し得る所(再試行、付け直した要素)では蓄積に冪等性のキーを持たせること。3.xの$scanの説明は3.5.4のREADMEにある。

Watch: $watch #

$renderedCallback is binding-driven: it reports the paths whose live DOM bindings were applied, so a value you never render is invisible to it. $watch, added in v1.27.0, is the headless counterpart — it fires on state changes whether or not anything on the page is bound to the path.

$renderedCallbackはバインディング駆動で、ライブなDOMバインディングが適用されたパスしか報告しない。描画していない値には届かない。v1.27.0で追加された$watchはそのヘッドレス版で、パスがどこにバインドされていてもいなくても、状態の変化で発火する。

state.js$watch
export default {
  isLoading: false,
  items: [],
  $listKeys: { items: "id" },   // a refetch fires only the rows whose fields changed

  $watch: {
    // edge detection is yours: compare cur / prev
    isLoading(cur, prev) {
      if (cur === true && prev === false) { this.startedAt = Date.now(); }
    },
    // wildcard paths fire once per changed row; trailing args are loop indexes
    "items.*.price"(cur, prev, index) {
      this.lastPriceChange = `#${index}: ${prev} → ${cur}`;
    }
  }
};

The handler runs with this bound to a writable state proxy; its writes land in the next update batch, and chains of mutually-writing watches are cut at 32 links. prev is the value at the start of the batch and is scalar-only — it reuses the read the same-value guard already does, so watch costs no extra read, and it is undefined for reference types. Watching a computed getter makes it eager: evaluated at connect and at the end of every batch that touches its dependencies, so an unrendered computed can fire at all. 4.0: a watched getter’s prev is its previous evaluation, and a watched wildcard getter (items.*.tax) is evaluated for every row of its list, rendered or not — keep it cheap and free of side effects. Handler exceptions are isolated — reported to the console (and the devtools timeline), while the remaining watches still run. SSR never runs watches.

ハンドラのthisは書き込み可能なstateプロキシで、書き込みは次の更新バッチに乗る。相互に書き合うwatchの連鎖は32段で打ち切られる。prevはバッチ開始時点の値でスカラー限定 — same-value guardが既に行う読み取りを再利用するため追加コストがなく、参照型ではundefinedになる。算出getterをwatchするとeagerになり、接続時と依存が動いたバッチの終わりに毎回評価される — 描画されていない算出値が発火できるのはこのため。4.0: watchしたgetterのprevはその前回の評価で、watchしたワイルドカードのgetter(items.*.tax)は、描かれていてもいなくてもリストの全行について評価される — 軽く、副作用の無いものに保つこと。ハンドラ内の例外は隔離され、コンソール(とdevtoolsタイムライン)に報告された上で残りのwatchは実行される。SSRではwatchは動かない。

v3.4.0: there are two chain limits now. The $watch chain is counted per write: a handler, a $scan fold or a $stream restart fires at the depth of the write that triggered it, so a handler that follows a long finite render chain (a $renderedCallback shrinking a heading one step per render) is no longer cut off at the 34th value, while mutually-writing handlers — and a loop through a $stream restart, which used to run without end — are still cut after 32 links. And a chain of writes made while bindings are applied — a row element handing its initial value to state, a $renderedCallback write — is cut after 100 links: the batch past the limit is not rendered (its values stay in the state), one console.error names its paths (render chain depth limit exceeded; bindings for this batch were not applied.), and DevTools receives state:render-chain-limit, which its timeline shows as a render-chain-limit warning row. Writes from $watch, $scan and $stream restarts carry that chain over, so a render loop through them is cut too, and finite chains joined that way share the 100 links. A write from outside the drain — a user action, a timer, a $stream value, an await continuation — starts from zero, so an element that reports from a microtask and an async $renderedCallback stay outside the limit. An element swap whose two writes run in separate updates now fires items.* for the position the completing update wrote, with that position’s prev. 4.0: past the 32-link limit only the handlers and restarts those writes fired are skipped, and the batch’s other handlers still run (3.x skipped the whole batch); a restart’s writes count toward the render chain too, so element write-backs that restart a stream a microtask apart are cut after about 50 renders. Tooling follows the declaration: @wcstack/lint and the VS Code extension check every $watch key statically (wcs/watch-declaration-invalid, wcs/watch-path-missing) — worth heeding, because a $watch typo does not fail visibly the way a binding typo does; it just never fires. The devtools timeline records watch-error and watch-chain-limit events, and as of v1.29.0 firing itself is measured: the runtime emits state:watch-fired, and the devtools coverage tab joins declared keys against it — each path shows fired ×N, never, or prerequisite-missing, kept distinct from “never”. Shadow DOM component

bind-component="state" binds the element's own state field as the state source.

my-component.jsShadow DOM
class MyComponent extends HTMLElement {
  state = { message: "" };

  constructor() {
    super();
    this.attachShadow({ mode: "open" });
    this.shadowRoot.innerHTML = `
      <wcs-state bind-component="state"></wcs-state>
      <div>{{ message }}</div>
      <input type="text" data-wcs="value: message" />
    `;

Light DOM component

In v2 a Light DOM component is written exactly like the Shadow one — no name, no @ references. Scope is decided by position in the DOM, so the v1 rule “two instances carrying the same name cannot share a scope, use Shadow DOM for a component stamped on every row” is gone with the registry that caused it: the same Light DOM component can sit on every row of a list. The host must wire it, though — a plain, unwired Light DOM bind-component cannot exist in v2, because an independent tree cannot share the parent’s root; it fails loudly with the fix (attach a shadow root, or mount it from the host). getBindingsReady(root) now covers mounted scopes once the mount record resolves.

v2ではLight DOMコンポーネントはShadowと完全に同じ書き方になる — nameも@参照も要らない。スコープはDOM上の位置で決まるので、「同じnameの2インスタンスは1スコープに共存できない、リストの各行に置くならShadow DOMを使え」というv1の制約は、その原因だったレジストリごと消えた。同じLight DOMコンポーネントをリストの全行に置ける。ただしホストが必ず配線すること — 配線のない素のLight DOM bind-componentはv2では存在できない(独立した木は親のルートを共有できないため)。修正方法つきで大きく失敗する(shadow rootを付けるか、ホストからマウントする)。getBindingsReady(root)はマウント記録が解決すればマウント配下も覆う。

Whole-object mount: state: path

Instead of wiring property by property, mount a whole subtree as the component’s root — inside the component every path is relative to the mount point: <user-card data-wcs="state: user"> makes name inside be user.name (reads, writes, getters and for: included). In a loop, mount the row itself: <user-row data-wcs="state: .">. Partial mounts coexist by longest prefix (state: user; state.theme: theme), and the component’s unmapped own keys stay private (rule R1). An array cannot be the mount root — mount the row or the object holding the array. 3.0: an explicit partial mount wins over the component’s own key — a component that declares a default for a mapped key (state = { message: "" } with state.message: user.name) reads the host value, and the default is simply not used (in 2.x the default won, with a wcs/mount-own-key-shadow warning). And #ro on a mount is honoured: with state#ro: user or state.title#ro: doc.title the component can read the entry but not write it — an assignment, $setAll or a writing $resolve throws [wcs/mount-readonly], and a two-way input inside does not write back, while the host can still write the path (2.x accepted the modifier and ignored it).

プロパティを1つずつ結線する代わりに、サブツリー全体をコンポーネントのルートとしてマウントする — 内側ではすべてのパスがマウント点からの相対になる。<user-card data-wcs="state: user">なら内側のnameはそのままuser.name(読み・書き・getter・for:を含む)。ループでは行そのものをマウントする: <user-row data-wcs="state: .">。部分マウントは最長プレフィクス勝ちで共存し(state: user; state.theme: theme)、コンポーネント自身のマップされていないキーはprivateのまま(規則R1)。配列をマウントルートにはできない — 行か、配列を持つオブジェクトをマウントする。3.0: 明示的な部分マウントはコンポーネント自身のキーに勝つ — マップされたキーに既定値を宣言したコンポーネント(state.message: user.nameとstate = { message: "" })はホストの値を読み、既定値は単に使われない(2.xでは既定値が勝ち、wcs/mount-own-key-shadowで警告された)。そしてマウントの#roが守られる: state#ro: userやstate.title#ro: doc.titleなら、コンポーネントはその項目を読めるが書けない — 代入・$setAll・書き込みの$resolveは[wcs/mount-readonly]をthrowし、中の双方向の入力も書き戻さない。ホストは今もそのパスに書ける(2.xは修飾子を受け取って無視していた)。

v3.3.0: only a one-segment entry marks a component key as mapped, so a deep partial mount (state.a.b: outer.b) no longer makes a.c read the host. A component’s own method wins over a partial mount of the same name again (state.save: x had made save() uncallable), and a partial entry the component’s own surface hides is reported once as wcs/mount-own-key-shadow. A class-based component keeps its prototype accessors: a getter whose name also exists on the host tree under the mount point now wins inside the component, as it already did for an object-literal state.

The wc-bindable protocol #

Custom elements expose a static manifest — observable properties, settable inputs, invocable commands — so any binding core can discover and wire them generically. All 30+ wcstack I/O nodes speak it; so can yours.

静的マニフェスト(properties / inputs / commands)を公開すれば、どのバインディングコアからも汎用的に結線できる。

my-chip.jsManifest
class MyChip extends HTMLElement {
  static wcBindable = {
    protocol: "wc-bindable",
    version: 1,
    properties: [
      { name: "data", event: "thing-error" }
    ],
    inputs: [
      { name: "data", attribute: "data" },
      { name: "labelText", attribute: "label-text" },
      { name: "internal" }
    ],
    commands: [
      { name: "fetch", async: true },
      { name: "reset" }
    ]
  };
}

Inputs and the attribute hint (4.0: property only)

4.0 writes an input’s property, and only the property. An entry’s optional attribute names the HTML attribute that corresponds to the property in markup (<my-chip label-text="…">); the protocol defines it as a declaration for tooling, and reflecting a property to its attribute — for attributeChangedCallback, CSS attribute selectors or DevTools — is the element’s job, in its setter, with the encoding only the element knows (a boolean as a present / absent attribute, "on" / "off", JSON …). This is wc-bindable 0.10’s applier profile, A1. 3.x also wrote the attribute after the property (String(value), JSON for an object or array, removed for null / undefined), and that copy fought the element’s own: a false written as "false" turned on the I/O nodes that read the attribute by its presence (<wcs-wakelock active>, <wcs-camera keep-alive>, the manual of the I/O nodes), and an attribute the element changed itself stayed stale. Every wcstack element reflects in its setter, so nothing changes for them; an element of your own that has no setter, or reads the input only in attributeChangedCallback, needs a setter that reflects it, and CSS that matched an attribute value state wrote ([active="false"]) now sees the element’s own encoding.

4.0は入力のプロパティに、プロパティにだけ書く。 エントリの省略可能なattributeは、マークアップでそのプロパティに対応するHTMLの属性を名指すもの(<my-chip label-text="…">)で、プロトコルはそれをツールのための宣言と定めている。プロパティを属性へ反映するのは — attributeChangedCallbackやCSSの属性セレクタやDevToolsのために — 要素の仕事で、setterの中で、要素だけが知る符号化(真偽値なら属性の有無、"on" / "off"、JSON…)で行う。wc-bindable 0.10のapplierプロファイルのA1だ。3.xはプロパティの後で属性にも書いていた(String(value)、オブジェクトや配列はJSON、null / undefinedなら取り除く)が、その写しは要素自身のものとぶつかっていた: "false"と書かれたfalseは、属性の有無で読むI/Oノード(<wcs-wakelock active>、<wcs-camera keep-alive>、I/Oノードのmanual)をオンにし、要素が自分で変えた属性は古いまま残った。wcstackの要素はどれもsetterで反映するので、それらには何も変わらない。setterを持たない自作の要素や、入力をattributeChangedCallbackでしか読まない要素には、それを反映するsetterが要る。stateが書いた属性の値に合わせていたCSS([active="false"])は、いまは要素自身の符号化を見る。

my-chip.js4.0: the element reflects in its setter
class MyChip extends HTMLElement {
  static wcBindable = {
    protocol: "wc-bindable", version: 1,
    properties: [],
    inputs: [
      { name: "labelText", attribute: "label-text" }, // markup: <my-chip label-text="…">
      { name: "selected", attribute: "selected" },    // markup: <my-chip selected>
    ],
  };
  get labelText() { return this.getAttribute("label-text") ?? ""; }
  set labelText(v) { v == null ? this.removeAttribute("label-text") : this.setAttribute("label-text", v); }
  get selected() { return this.hasAttribute("selected"); }
  set selected(v) { this.toggleAttribute("selected", Boolean(v)); }
}

null and undefined on an I/O node’s input (4.0). Every wcstack I/O node handles both as wc-bindable 0.10’s producer guidance asks: null removes the input’s attribute (its documented default), undefined restores the attribute the element started with (the markup value, or none), and neither is written as the string "null" / "undefined" — 3.x’s String(value) made <wcs-sse>, <wcs-ws> and <wcs-worker> open undefined. @wcstack/state never writes undefined to an input (an undefined path skips the write, stricter than the profile’s A2), so a page bound with it sees a difference only where it writes null: a boolean that is on by default (<wcs-audio>’s limiter, <wcs-debounce>’s trailing, <wcs-throttle>’s leading) goes back on instead of off.

I/Oノードの入力へのnullとundefined(4.0)。 wcstackのI/Oノードはどれも、wc-bindable 0.10のプロデューサー向けの指針どおりに両方を扱う: nullは入力の属性を取り除き(文書にある既定値)、undefinedは要素が最初に持っていた属性(マークアップの値、または無し)を戻し、どちらも文字列"null" / "undefined"としては書かれない — 3.xのString(value)は、<wcs-sse>・<wcs-ws>・<wcs-worker>にundefinedを開かせていた。@wcstack/stateは入力にundefinedを決して書かない(undefinedのパスは書き込みを飛ばす。プロファイルのA2より厳しい)ので、それでバインドしたページに違いが見えるのはnullを書く所だけだ: 既定でオンの真偽値(<wcs-audio>のlimiter、<wcs-debounce>のtrailing、<wcs-throttle>のleading)は、オフではなくオンに戻る。

Binding authority (#init= / #sync=)

For wc-bindable elements, the modifier decides which side owns the wire:

AuthorityEffect
init=stateState writes to element; element events update state (two-way)
init=elementElement snapshot + events → state; state writes suppressed
init=autoElement-owned if uninitialized, else state-owned
init=noneNo initial sync (event bindings only)

sync=call (default) reads the snapshot immediately; sync=connect defers until DOM connection.

Directional initial sync rule: declare every settable member in both properties and inputs for two-way. Output-only members declared only in properties become element-owned — state writes are suppressed. The rule is on by default; in 4.0 a state tree opts out with $behavior: { enableDirectionalInitialSync: false } (it was a bootstrapState() option), and then #init= / #sync= throw (#31) and state wins every initial sync.

双方向にしたいメンバーはpropertiesとinputsの両方に宣言する。propertiesのみのメンバーは出力専用(要素側が所有)。この規則は既定で有効で、4.0ではstateの木ごとに$behavior: { enableDirectionalInitialSync: false }で外す(以前はbootstrapState()のオプションだった)。そのとき#init= / #sync=はthrowし(#31)、初期同期はすべてstateが勝つ。

v3.4.0: an element-owned member in a for: row takes its initial value from its own element again — on a render whose rows were all new it threw and left the list empty (see Loop). Inside a shadow root with a scoped CustomElementRegistry, the elements of for: rows take their definitions from that registry: the first rows of a render were activated in a DocumentFragment, where Chromium reports the global registry, so their property bindings and spreads stayed empty until the same name was defined globally, and the listeners of two-way and output members never reached state — as in 3.3.0. An #init=element or output-only member also keeps the element’s own value in a row added later and in an if: branch.

v3.4.0: for:の行の中の要素所有のメンバーは、再び自分の要素から初期値を受け取る — 行がすべて新しい描画では、throwしてリストを空にしていた(Loopを参照)。スコープ付きのCustomElementRegistryを持つshadow rootの中では、for:の行の要素はそのレジストリから定義を受け取る: 描画の最初の行はDocumentFragmentの中で起動され、Chromiumはそこでグローバルのレジストリを返すので、同じ名前がグローバルに定義されるまでそのプロパティバインディングとspreadは空のままで、双方向や出力のメンバーのリスナーはstateに届かなかった — 3.3.0でも同じだ。#init=elementや出力専用のメンバーは、後から追加された行やif:の枝でも、要素自身の値を保つ。

Migrating from 3.x #

4.0 replaces the engine inside @wcstack/state. What you write against stays — <wcs-state>, data-wcs, {{ }} and comment bindings, for / if, paths and path getters, the $ APIs, bind-component, mount=, enable-ssr and the package entries — and there is no compatibility layer. Instead, 3.5 named each name and option 4.0 removes or moves with [wcs/v4-migration], and its lint warns about several forms 4.0 rejects, while still running them the 3.x way; a few changes nothing reports (below). The path: upgrade to 3.5, clear its warnings — all but those for the three options that move to $behavior — then move every @wcstack/* package to 4.0 at once, @wcstack/server together with the client. Most replacements below can be written on 3.5 — all but $behavior, the list-keys feature and the 4.0 server — so the fixed page runs the same on 3.5 and on 4.0. The full guide, with the reason for each change, is docs/migration-v4.md.

Known limitation. One object at two positions of one list, or in two arrays no getter relates: a write below one of the rows does not reach the other row’s bindings and row getters; plain reads, root getters and $getAll see the new value. Call $postUpdate on the list after such a write, or replace the changed item instead of writing below it. It is to be fixed in 4.0.x. In one nested shape — two outer rows holding different arrays that share an object (#401) — 3.4 and 3.5 redrew the other outer row’s leaf bindings and 4.0 does not, so a page that relied on it needs the $postUpdate.

v2.5.1: reading a cached getter got a little cheaper. v4.0.0: the rewritten engine, built with esbuild and terser (build.mjs) instead of tsc + Rollup, is smaller as well as faster. Gzip, 3.5.4 → 4.0: auto.min.js 88,005 → 47,715 B (−46 %), dist/index.esm.js 90,932 → 50,653 B (−44 %), the split /core with its chunks 59,334 → 24,500 B (−59 %), and the core alone (dist/core.min.js, built for the size gate and not published) 19,846 B against its 20 KiB (20,480 B) target. The wcstack/auto entry bundle (state, router, fetch, storage and the autoloader in one file) goes from 109,793 to 69,627 B gzip (−37 %), 373.8 → 217.6 KB min. Three scaling problems are gone with it. A list whose items repeat no longer goes quadratic — a 90,000-cell board from 4.6 s to 6 ms. Paths built from data (this["usersById." + this.selectedId], $resolve("dict." + key, [])) no longer accumulate: a top-level getter depends on what its last evaluation read, and after each update the patterns only such paths made that nothing holds are dropped, so replacing the object under them no longer costs the number of keys ever used. And emptying a list, swapping an if: branch or removing a multi-node row under happy-dom — the DOM of @wcstack/testing and @wcstack/server — is no longer quadratic: a list that is all its parent holds is emptied with one replaceChildren(), 14 % faster than a Range in Chromium on 10,000 rows, where emptying 1,000 rows took 15 s in a test.
