What's New

Shipped in v4.0.0 → v4.0.1

4.0 replaces the engine inside @wcstack/state with a rewritten one — a smaller core and faster updates behind the same markup. <wcs-state>, data-wcs, {{ }} and comment bindings, for / if, path getters, the $ APIs, bind-component, mount=, enable-ssr and the package entries all stay; auto.min.js goes from 88.0 to 47.7 KB gzip (−46 %), and on the official js-framework-benchmark the CPU-weighted geometric mean is 1.07, against 1.44 for 3.5.4 and 1.22 for @wcstack/signals (vanillajs: 1.02). Most of what changes is what 3.5 announced: 4.0 removes what 3.2 renamed and what 3.5 warned about ($scan, the old names, substr, three bootstrapState() options), moves three more options into each state’s $behavior, delegates the common on*: events to the root, and every package’s bootstrapXxx(config) now throws on an option it does not have. There is no compatibility layer: upgrade to 3.5, clear its warnings, then move every @wcstack/* package to 4.0 at once — @wcstack/server together with the client — following the migration table and the 3.x → 4.0 migration guide. Every published package moves to 4.0.0; outside @wcstack/state, the I/O nodes now handle null and undefined written to an input, and the router, <wcs-defined>, <wcs-throttle>, <wcs-camera>, <wcs-wakelock>, <wcs-ws>, <wcs-audio> and DevTools bring fixes with them. The VS Code extension ships the 4.0 rules as 2.0.0; keep 1.21.x, @wcstack/lint 3.5 and @wcstack/typescript 3.5 for 3.x projects. The rest — the numbers, the scaling fixes and what each 3.x release did — is in Performance and the version notes of the state page. v4.0.1 comes from writing the tutorial: a class: or attr: without a name, which did nothing, is refused by name (#122), and the lint stops reporting the fields of a list that a getter returns (for: visible) and reports an unknown filter as an error, as the runtime throws on it.

4.0は@wcstack/stateの中のエンジンを書き直したものに置き換える — 同じマークアップの裏で、より小さなコアとより速い更新を。<wcs-state>、data-wcs、{{ }}とコメントバインディング、for / if、パスgetter、$のAPI、bind-component、mount=、enable-ssr、パッケージのエントリはどれもそのままだ。auto.min.jsは88.0から47.7 KB gzipへ(−46 %)、公式のjs-framework-benchmarkでのCPUの重み付き幾何平均は1.07で、3.5.4は1.44、@wcstack/signalsは1.22だ(vanillajsは1.02)。変わるものの大半は3.5が予告したものだ: 4.0は3.2が改名したものと3.5が警告したもの($scan、旧名、substr、bootstrapState()の3つのオプション)を取り除き、さらに3つのオプションを各stateの$behaviorへ移し、よく使うon*:のイベントをルートに委譲する。そして各パッケージのbootstrapXxx(config)は、持っていないオプションでthrowするようになる。互換層は無い: 3.5に上げ、その警告を消し、それから@wcstack/*のパッケージをすべて一度に4.0へ移す — @wcstack/serverもクライアントと一緒に — 手順は移行表と3.x → 4.0移行ガイドにある。公開しているパッケージはすべて4.0.0になる。@wcstack/stateの外では、I/Oノードが入力に書かれたnullとundefinedを扱うようになり、ルーター・<wcs-defined>・<wcs-throttle>・<wcs-camera>・<wcs-wakelock>・<wcs-ws>・<wcs-audio>・DevToolsにも修正が入る。VS Code拡張は4.0の規則を2.0.0として出す。3.xのプロジェクトでは1.21.x、@wcstack/lint 3.5、@wcstack/typescript 3.5を使い続けること。残り — 数値、規模に関わる修正、3.xの各リリースがしたこと — はPerformanceとstateのページの版ごとの注記にある。v4.0.1はチュートリアルを書く中で見つかったものを直す: 名前の無いclass:やattr:は何もしなかったが、名指しで拒まれる(#122)。lintは、getterが返すリストのフィールド(for: visible)を報告しなくなり、未知のフィルタはランタイムがthrowするとおりerrorとして報告する。

v4.0.0 <wcs-state>

A new engine behind the same markup

What if the engine were rewritten from scratch — and no page had to change a tag?

4.0 keeps everything you write against and replaces what runs it. A path resolves to a pattern and a row; a write dirties the getters that read it and queues the bindings under it; a microtask drain re-syncs the lists and applies them. Built with esbuild and terser instead of tsc + Rollup, auto.min.js is 47.7 KB gzip (88.0 in 3.5.4), dist/index.esm.js 50.7 KB (90.9), the split /core with its chunks 24.5 KB (59.3) — the core alone 19.8 KB against a 20 KiB target — and the wcstack/auto bundle 69.6 KB (109.8). On the official js-framework-benchmark (4.0.0-rc.7, all four in one session) the CPU-weighted geometric mean is 1.07, against 1.44 for 3.5.4, 1.22 for @wcstack/signals and 1.02 for vanillajs; the JavaScript time is about a third of 3.5.4’s, and 1,000 rows hold 2.97 MB instead of 6.35. Scaling went with it. A list whose items repeat — a board of 0 / 1 cells, tags, numbers — no longer goes quadratic: a 90,000-cell board from 4.6 s to 6 ms, and changing two cells rebuilds two rows. Paths built from data (this["usersById." + id]) no longer leave one pattern per key ever used, and emptying a 1,000-row list under happy-dom — the DOM of @wcstack/testing and @wcstack/server — no longer takes 15 s. The new engine also closes issues open against 3.x: a getter reading the adjacent item (#2), update loops past 3.x’s render-chain limit (#353), reads and writes through for: groups.0.items (#363), hydrated Light DOM children and getter if:s (#372, #375), inner arrays shared by several rows (#396–#398), and part of the TodoMVC shape (#365).

4.0は、書く側が向き合うものをすべて残し、それを動かすものを取り替える。パスはパターンと行に解決され、書き込みはそれを読むgetterを汚してその下のバインディングをキューに積み、マイクロタスクのドレインがリストを同期し直して適用する。tsc + Rollupの代わりにesbuildとterserでビルドし、auto.min.jsは47.7 KB gzip(3.5.4では88.0)、dist/index.esm.jsは50.7 KB(90.9)、分割形の/coreはチャンク込みで24.5 KB(59.3) — コアだけなら20 KiBの目標に対して19.8 KB — wcstack/autoのバンドルは69.6 KB(109.8)になった。公式のjs-framework-benchmark(4.0.0-rc.7、4つを同じセッションで計測)でのCPUの重み付き幾何平均は1.07で、3.5.4は1.44、@wcstack/signalsは1.22、vanillajsは1.02だ。JavaScriptの時間は3.5.4の約3分の1で、1,000行が持つメモリは6.35 MBではなく2.97 MBだ。規模への強さもついてきた。要素が繰り返すリスト — 0 / 1のセルの盤面、タグ、数値 — はもう二乗にならない: 9万セルの盤面は4.6 sから6 msになり、2つのセルを変えれば作り直すのは2行だ。データから組み立てたパス(this["usersById." + id])が、これまで使ったキーの数だけパターンを残すことももう無く、happy-dom — @wcstack/testingと@wcstack/serverのDOM — の下で1,000行のリストを空にするのに15 sかかることも無い。新しいエンジンは3.xに対して開いていたissueも閉じる: 隣の要素を読むgetter(#2)、3.xの描画連鎖の上限を越える更新のループ(#353)、for: groups.0.items越しの読み書き(#363)、ハイドレートしたLight DOMの子とgetterのif:(#372、#375)、複数の行が共有する内側の配列(#396–#398)、そしてTodoMVCの形の一部(#365)だ。

  • CPU 1.07 vs 1.44
  • 90,000 Cells: 4.6 s → 6 ms
v4.0.0 $behavior: { enableMustache: false }

What 3.5 announced, done

What if every warning of the last minor turned into exactly one error, named where you wrote it?

4.0 removes what 3.5 named with [wcs/v4-migration]. $scan is gone — fold in a $watch or $on handler — and so are the names 3.2 renamed (the filters inc dec fix uc lc cap rep rev pad null, $trackDependency / $untrackDependency, $updatedCallback / $streams), the substr filter (slice(start, start + length)), and the bootstrapState() options debug, commentTextPrefix and enablePropagationContext. A removed filter name fails with [wcs/filter-unknown] naming its replacement, not a did-you-mean (dec → eq would change the meaning). Configuration is split: bootstrapState() keeps how the page spells the markup — bindAttributeName, tagNames, the anchor-comment prefixes — plus locale and enableContractAnalyzer, while enableMustache, sameValueGuard and enableDirectionalInitialSync move to the $behavior of each root state: booleans, true by default, also on /auto pages, which had no way to pass them in 3.x, and in JSON states. An unknown key or a non-boolean throws #44, a re-set that changes it #45. Every package’s bootstrapXxx(config) throws on an option it does not have — bootstrapState() and the 41 others: an unknown key, a value of another type (null or an array included), a tagNames key the package does not define. Every option is checked before any is applied, and pages that only load /auto pass no options. Failures are reported once: <wcs-state src="./state.js"> failed to initialize. (#49), and a $connectedCallback that fails once the bindings are built as … $connectedCallback failed. (#50) — connectedCallbackPromise rejects, getBindingsReady() resolves. An unreadable src="*.json" and a state="id" with no such script reject instead of starting empty, and a markup error at page level stops initialization there: what comes before it is bound, what comes after it is not.

4.0は3.5が[wcs/v4-migration]で名指ししたものを取り除く。$scanは無くなり — $watchか$onのハンドラで畳み込む — 3.2が改名した名前(フィルタinc dec fix uc lc cap rep rev pad null、$trackDependency / $untrackDependency、$updatedCallback / $streams)、substrフィルタ(slice(start, start + length))、bootstrapState()のオプションdebug・commentTextPrefix・enablePropagationContextも無くなる。取り除かれたフィルタ名は、did-you-meanではなく置き換え先を名指しする[wcs/filter-unknown]で失敗する(dec → eqでは意味が変わってしまう)。設定は分かれた: bootstrapState()に残るのはページがマークアップをどう綴るか — bindAttributeName、tagNames、アンカーのコメントの接頭辞 — とlocale・enableContractAnalyzerで、enableMustache・sameValueGuard・enableDirectionalInitialSyncは各ルートのstateの$behaviorへ移る。真偽値で既定はtrue、3.xでは渡す手段の無かった/autoのページでも、JSONのstateでも書ける。未知のキーや真偽値でない値は#44を、それを変える再セットは#45をthrowする。各パッケージのbootstrapXxx(config)は、持っていないオプションでthrowする — bootstrapState()と他の41個: 未知のキー、型の違う値(nullや配列も含む)、パッケージが定義していないtagNamesのキーだ。どのオプションも適用の前にすべて検査され、/autoだけを読み込むページはオプションを渡さない。失敗は一度だけ報告される: <wcs-state src="./state.js"> failed to initialize.(#49)、そしてバインディングを組み立てた後に失敗した$connectedCallbackは… $connectedCallback failed.(#50)として — connectedCallbackPromiseはrejectし、getBindingsReady()はresolveする。読めないsrc="*.json"と、そのスクリプトが無いstate="id"は、空のstateで始める代わりにrejectし、ページ直下のマークアップのエラーは初期化をそこで止める: それより前はバインドされ、後はされない。

  • $behavior per Root State

  • Failures Reported Once
v4.0.0 onclick#direct,stop: save

One listener per event type

What if a thousand rows of buttons needed one click listener, not a thousand?

on*: bindings of click, dblclick, input, change, submit, keydown, keyup, mousedown, mouseup, pointerdown and pointerup are delegated: one listener per type sits on the root the state binds — the document, a shadow root, or a Light DOM component’s host — and runs the handlers of the elements the event passed, innermost first. Four things follow. event.currentTarget is that root, so find the element with event.target.closest(…) or use the loop index the handler receives. #stop still stops the on*: handlers further out, but not a listener your own code added to an ancestor, which ran before the event reached the root. An ancestor that calls stopPropagation() — a modal’s content keeping clicks from the overlay — keeps the handlers inside it from running. And an element moved under another root (a dialog moved to document.body) no longer runs them. on*#direct: keeps the 3.x behaviour for one binding: the listener sits on the element, per row inside for: / if:, and combines with #prevent and #stop — 3.x already accepted it, so pages could write it from 3.5 on. Two-way bindings, eventToken. bindings, other event types and an event a custom element dispatches with bubbles: false stay on the element. The 4.0 lint reports a delegated handler that reads currentTarget before its first await as wcs/delegated-current-target; it cannot see stopPropagation() in page code or elements you move between roots, so look for those yourself.

click・dblclick・input・change・submit・keydown・keyup・mousedown・mouseup・pointerdown・pointerupのon*:バインディングは委譲される: 種類ごとに1つのリスナーが、stateがバインドするルート — 文書、shadow root、あるいはLight DOMのコンポーネントのホスト — に置かれ、イベントが通った要素のハンドラを内側から順に走らせる。帰結は4つある。event.currentTargetはそのルートなので、要素はevent.target.closest(…)で探すか、ハンドラが受け取るループのインデックスを使う。#stopは今も外側のon*:ハンドラを止めるが、自分のコードが祖先に付けたリスナーは止めない。それはイベントがルートに届く前に走っているからだ。stopPropagation()を呼ぶ祖先 — オーバーレイにクリックを届かせないモーダルの中身 — は、その内側のハンドラを走らせない。そして別のルートの下へ動かした要素(document.bodyへ動かしたダイアログ)は、もうそれを走らせない。on*#direct:はバインディング1つについて3.xの挙動を保つ: リスナーは要素に付き、for: / if:の中では行ごとに付き、#prevent・#stopと組み合わせられる — 3.xもすでに受け付けていたので、ページは3.5から書いておけた。双方向バインディング、eventToken.バインディング、それ以外の種類のイベント、カスタム要素がbubbles: falseで送るイベントは要素に残る。4.0のlintは、最初のawaitより前にcurrentTargetを読む委譲されたハンドラをwcs/delegated-current-targetとして報告する。ページのコードのstopPropagation()や、ルートの間で動かす要素は見えないので、それは自分で探すこと。

  • currentTarget Is the Root
  • #direct Opts One Binding Out
  • Two-Way Stays on the Element
v4.0.0 this["items.0"] = item

A row stays where it is

What if writing a list element changed what that row shows — and nothing moved?

Writing a list element (this["items.0"] = …, $resolve("items.*", [0], v)) replaces the value at that position: the row stays where it is, with its $1 and the DOM state the bindings do not own — focus, text typed into an unbound input, an open <details> — and everything derived below it is computed again. 3.x moved rows with their values once a swap completed; to move rows now, assign a new array, and rows follow their objects by identity. for: takes no filters: for: items|take(2) fails with [wcs/binding-syntax] #121, because the rows of a filtered array would name other elements and writes through them would land on the wrong ones — loop over a getter that returns the list instead. A write reaches both sides of such a getter: in the TodoMVC shape (get shown() returning a filtered copy of todos, rendered with for: shown), a checkbox writing .done updates the todos row, $getAll("todos.*.done") and the filter itself, so the checked row leaves the “active” view (#365). A numeric segment is an index only under an array: sales.2024.total and usersById.42.name are keys, spelled as written, in markup, this[…], $eq and $watch (#382), and an index past the end of a list reads undefined. Row and branch clones lose their data-wcs attribute (use a class for CSS and test selectors), outerHTML: / outerText: inside a template fail with #203 (bind innerHTML: on a wrapper), and a * of another list inside a row with #1403. One limitation stays, to be fixed in 4.0.x: one object at two positions of one list, or in two arrays no getter relates — call $postUpdate after a write below it.

リストの要素への書き込み(this["items.0"] = …、$resolve("items.*", [0], v))はその位置の値を置き換える: 行はその場にとどまり、$1も、バインディングが持たないDOMの状態 — フォーカス、バインドしていない入力欄に打ち込んだ文字、開いた<details> — もそのままで、その下で導かれるものはすべて計算し直される。3.xはswapが完了すると行を値ごと動かしていた。いま行を動かすには新しい配列を代入する。行は同一性でオブジェクトについていく。for:はフィルタを取らない: for: items|take(2)は[wcs/binding-syntax] #121で失敗する。フィルタを通した配列の行は別の要素を名指してしまい、その行を通した書き込みが違う要素に落ちるからだ — 代わりにリストを返すgetterの上で回す。そうしたgetterの両側に書き込みは届く: TodoMVCの形(todosの絞り込んだコピーを返すget shown()をfor: shownで描く)では、.doneに書くチェックボックスがtodosの行、$getAll("todos.*.done")、そして絞り込みそのものを更新するので、チェックした行は「未完了」のビューから外れる(#365)。数値の区間が添字になるのは配列の下だけだ: sales.2024.totalやusersById.42.nameは書いたとおりのキーで、マークアップでもthis[…]でも$eqでも$watchでも同じだ(#382)。リストの末尾を越えた添字の読みはundefinedになる。行と枝の複製はdata-wcs属性を持たず(CSSやテストのセレクタにはクラスを使う)、テンプレートの中のouterHTML: / outerText:は#203で(ラッパーにinnerHTML:をバインドする)、行の中の別のリストの*は#1403で失敗する。制限が1つ残り、4.0.xで直される予定だ: 1つのリストの2つの位置にある1つのオブジェクト、あるいはgetterが関係づけていない2つの配列にあるオブジェクト — その下へ書いた後に$postUpdateを呼ぶこと。

v4.0.0 "items.*.price"(cur, prev, i)

Watches that need no for:

What if a row watch fired for every row that changed — rendered or not?

A row watch is headless now. $watch: { "items.*.price"(cur, prev, i) { … } } fires for a list the page does not render: 4.0 keeps the lists a row watch ranges over in step by itself, where 3.x, with neither a for: nor $listKeys, fired it zero times. A watch on a row getter (items.*.total) is evaluated eagerly for every row, rendered or not, and its prev is that row’s previous value — 3.x fired it only where the getter was bound, with prev always undefined — so keep a watched row getter cheap. Assigning a whole array fires only the rows that came in, matched by identity, and a kept row’s getter watch only when its value changed (#389); a re-sort fires no data row watch. A key with a numeric index ("items.0.v") fires only when the value at that index changes, and writing an element of an array several outer rows share fires once for every outer row that holds it, each with its own indexes. Loops are cut instead of freezing the page: what a $stream run writes in the task it started in continues its chain for the $watch handlers it fires, so a $watch → $stream loop over a source that yields at once (an async generator over memory, a ReadableStream that enqueues in start) stops after about 16 laps and is reported once. Past the chain limit, only the handlers and restarts those writes fired are skipped, and one update that does not settle within 32 passes is stopped and reported. $scan is gone: keep the accumulation as an ordinary key and write it from $watch or $on.

行のwatchはいまヘッドレスだ。$watch: { "items.*.price"(cur, prev, i) { … } }は、ページが描いていないリストでも発火する: 4.0は行のwatchがまたがるリストを自分で歩調を合わせて保つ。3.xではfor:も$listKeysも無いと一度も発火しなかった。行getter(items.*.total)へのwatchは、描かれていてもいなくても全行について先行して評価され、そのprevはその行の前の値だ — 3.xはgetterがバインドされている所でしか発火せず、prevは常にundefinedだった — なので、watchする行getterは軽く保つこと。配列全体の代入が発火させるのは、同一性で照合して新しく入った行だけで、保たれた行のgetterのwatchは値が変わったときだけ発火する(#389)。並べ替えはデータの行のwatchを発火させない。数値の添字を持つキー("items.0.v")は、その添字の値が変わったときだけ発火し、複数の外側の行が共有する配列の要素への書き込みは、それを持つ外側の行ごとに、それぞれのインデックスで一度ずつ発火する。ループはページを止める代わりに打ち切られる: $streamの実行が始まったタスクの中で書いたものは、それが発火させる$watchハンドラについても連鎖を引き継ぐので、すぐに値を出すソース(メモリの上の非同期ジェネレータ、startでenqueueするReadableStream)を経る$watch → $streamのループは約16周で止まり、一度報告される。連鎖の上限を越えると、飛ばされるのはその書き込みが発火させたハンドラと再起動だけで、32回のパスで落ち着かない1つの更新は止められて報告される。$scanは無くなった: 蓄積は普通のキーとして持ち、$watchか$onから書くこと。

  • Row Watches Without for:
  • Row Getters Eager, prev Real
  • Whole Arrays Fire New Rows
  • Stream Loops Cut at ~16 Laps
v4.0.0 onclick: cart.checkout

Volumes hold data, components run their own

What if a module held only its data — and a component ran everything it declares?

A volume (<wcs-state mount="cart">) holds data, getters, setters and methods, and may declare $connectedCallback / $disconnectedCallback. It no longer runs the declarations that react to the whole tree: one that declares $watch, $listKeys, $renderedCallback, $behavior or $features is not grafted, and console.error says $watch is not run in a volume — declare it on the root state. — write it there with the full path ("cart.total"(cur) { … }). It takes no injections either: any data-wcs on the volume element refuses it, so read the root path in a root getter (this["cart.subtotal"] * (1 + this["settings.taxRate"])). In return, a volume’s methods are reachable by path — onclick: cart.checkout, this["cart.checkout"](). A mounted component (bind-component with state: …) goes the other way: it runs $listKeys, $commandTokens, $eventTokens, $on and $errorCallback on its own lists and bindings, and its own $behavior / $features, where 3.x warned and ran none; $recursion there throws, and $watch / $stream / $renderedCallback still belong to the root. An element write of the host row keeps the component and its private keys (#385, #386). A component host the page did not bind — inserted by code, or taken out before the page’s state loaded — is wired when its <wcs-state bind-component> connects, where 3.x waited forever, and a component wired to a root that failed rejects instead of hanging.

ボリューム(<wcs-state mount="cart">)が持つのはデータ・getter・setter・メソッドで、$connectedCallback / $disconnectedCallbackを宣言できる。木全体に反応する宣言はもう動かさない: $watch・$listKeys・$renderedCallback・$behavior・$featuresを宣言したボリュームは接ぎ木されず、console.errorが$watch is not run in a volume — declare it on the root state.と告げる — それはルートに完全なパスで書く("cart.total"(cur) { … })。注入も受けない: ボリューム要素のdata-wcsはどれもそれを拒ませるので、ルートのパスはルートのgetterで読む(this["cart.subtotal"] * (1 + this["settings.taxRate"]))。その代わり、ボリュームのメソッドはパスで届く — onclick: cart.checkout、this["cart.checkout"]()。マウントされたコンポーネント(state: …を伴うbind-component)は逆へ向かう: 自分のリストとバインディングについて$listKeys・$commandTokens・$eventTokens・$on・$errorCallbackを動かし、自分の$behavior / $featuresも持つ。3.xは警告してどれも動かさなかった。そこでの$recursionはthrowし、$watch / $stream / $renderedCallbackは今もルートのものだ。ホストの行の要素への書き込みは、コンポーネントとその私有キーを保つ(#385、#386)。ページがバインドしなかったコンポーネントのホスト — コードが差し込んだもの、ページのstateが読み込まれる前に取り出されたもの — は、その<wcs-state bind-component>が接続したときに配線される。3.xは永久に待っていた。そして失敗したルートに配線されたコンポーネントは、止まったままにならずにrejectする。

  • Volume Methods by Path
  • Components Run Their Own Tokens
  • Unbound Hosts Wired on Connect
v4.0.0 <wcs-ssr version="4.0.0">

Server and client move together

What if a server-rendered page hydrated every row it drew — nested ones too?

4.0 writes a new server output and reads only its own. Rows, branches and text bindings are marked with comments (<!--wcs-p:wcs-t0-->, <!--wcs-[-->, <!--wcs-t:EXPR-->), what a binding rendered — innerHTML included — is in the HTML as it is, and 3.x’s data-wcs-ssr-id attributes and props table are gone. The client takes the snapshot’s data over the state it loads from its own source, skips $connectedCallback, and adopts the server’s rows and branches where they are, nested ones included — the 3.4 limitation that sent a nested for to a full client render is gone, and a custom element in them connects once. Form values go into the markup where they differ from it (a password’s value is left out), so the page shows them before it is bound. The output is not compatible across 3.x and 4.0: a 4.0 client discards a 3.x snapshot with one warning (<wcs-ssr version="3.5.4"> does not match 4.0.0 …) and renders the page on the client from its own state, so the page works but what the server did is done again; with the output of a server up to 3.5.2, a text binding outside templates also loses its filters there. A 4.0 server with a 3.x client is not supported. Deploy @wcstack/server 4.0 with the 4.0 client, purge HTML cached from 3.x, and keep the comments: a minifier’s removeComments breaks hydration. outerHTML: / outerText: are applied on the client, not on the server.

4.0は新しいサーバー出力を書き、自分の出力だけを読む。行・枝・テキストバインディングはコメントで印が付けられ(<!--wcs-p:wcs-t0-->、<!--wcs-[-->、<!--wcs-t:EXPR-->)、バインディングが描いたもの — innerHTMLも含めて — はそのままHTMLにあり、3.xのdata-wcs-ssr-id属性とプロパティの表は無くなった。クライアントは自分のソースから読み込んだstateにスナップショットのデータを重ね、$connectedCallbackを飛ばし、サーバーの行と枝を、入れ子のものも含めて、その場で引き取る — 入れ子のforをクライアントでの全描画に回していた3.4の制限は無くなり、その中のカスタム要素は一度だけ接続する。フォームの値はマークアップと違うところでマークアップに書かれる(パスワードの値は除く)ので、ページはバインドされる前からそれを示す。出力は3.xと4.0の間で互換が無い: 4.0のクライアントは3.xのスナップショットを警告1つ(<wcs-ssr version="3.5.4"> does not match 4.0.0 …)とともに捨て、自分のstateからクライアントでページを描く。ページは動くが、サーバーがしたことはもう一度行われる。3.5.2までのサーバーの出力では、テンプレートの外のテキストバインディングがそこでフィルタも失う。4.0のサーバーと3.xのクライアントの組み合わせはサポートされない。@wcstack/server 4.0を4.0のクライアントと一緒にデプロイし、3.xでキャッシュしたHTMLを捨て、コメントは残すこと: minifierのremoveCommentsはハイドレーションを壊す。outerHTML: / outerText:はサーバーではなくクライアントで適用される。

v4.0.0 command.showModal: $command.edit

Native elements take commands

What if a state opened a dialog the way it starts a fetch — by emitting a token?

Command tokens reach native elements. With the native-commands feature, which @wcstack/state and /auto include, command.<method>: subscribes a native element’s method from a fixed table — showModal / close on <dialog>, focus and scrollIntoView on any element, requestSubmit on <form>, showPicker on <input>, play / pause on <audio> / <video>, … — so the state opens a dialog or focuses an input without ever holding the element. A method outside the table throws [wcs/token-misconfigured] (#1205), and an emit whose first argument is an Event (onclick: $command.edit) calls the method with none, so close() does not get "[object PointerEvent]" as the dialog’s return value. 3.x refused native elements. The split build gains one-tag loading: dist/split/auto.js, from a version-pinned /npm/ path, loads the core and the features the page names — features="scopes diagnostics" on the root <wcs-state> for what must be there first, $features: ["temporal", "formats"] in each state for what it needs. $listKeys moves into a list-keys feature of its own, the core now carries the 10 condition filters (it answered only not), and on /core without features/diagnostics a message is its number and values (#501 "uc") instead of the code and the sentence — docs/state-errors.md lists the numbers.

コマンドトークンがネイティブ要素に届く。@wcstack/stateと/autoが載せているnative-commands機能があれば、command.<method>:は決まった表にあるネイティブ要素のメソッドを購読する — <dialog>のshowModal / close、あらゆる要素のfocusとscrollIntoView、<form>のrequestSubmit、<input>のshowPicker、<audio> / <video>のplay / pause、… — だからstateは要素を一度も持たずにダイアログを開き、入力欄にフォーカスする。表に無いメソッドは[wcs/token-misconfigured](#1205)をthrowし、最初の引数がEventであるemit(onclick: $command.edit)は引数無しでメソッドを呼ぶので、close()がダイアログの戻り値として"[object PointerEvent]"を受け取ることは無い。3.xはネイティブ要素を拒んでいた。分割形のビルドはタグ1つでの読み込みを得る: バージョンを固定した/npm/のパスから読むdist/split/auto.jsが、コアと、ページが名指しした機能を読み込む — 先にそろっている必要があるものはルートの<wcs-state>のfeatures="scopes diagnostics"に、各stateが要るものはそのstateの$features: ["temporal", "formats"]に書く。$listKeysは自分のlist-keys機能へ移り、コアはいま10個の条件フィルタを載せ(以前はnotだけだった)、features/diagnosticsの無い/coreでは、メッセージはコードと文ではなく番号と値になる(#501 "uc") — 番号の一覧はdocs/state-errors.mdにある。

v4.0.0 <wcs-wakelock data-wcs="active: awake">

An input is a property

What if a false written to a tag stayed false — as the element understands it?

State writes a custom element’s wc-bindable input to its property only. 3.x also wrote the attribute the input’s attribute hint names, but the protocol defines that hint as a declaration for tooling, and reflecting is the element’s job in its setter. The binder’s copy fought it: a false written as "false" turned on the I/O nodes that read the attribute by its presence — <wcs-wakelock active>, <wcs-camera keep-alive>, every manual — and an attribute the element changed itself stayed stale. Every wcstack element reflects in its setter; an element of your own that relied on state writing its attribute needs a setter that reflects it. The I/O nodes handle null and undefined as wc-bindable 0.10’s producer guidance asks: null removes the input’s attribute (its documented default), undefined restores the one the element started with, and neither becomes the string "null" / "undefined" — 3.x’s String(value) made <wcs-sse>, <wcs-ws> and <wcs-worker> open undefined and <wcs-storage> load the key "undefined". @wcstack/state never writes undefined; React 19, a direct assignment and @wcstack/signals’ bindInput do, and bindInput now writes it only after the signal had another value. Fixes ride along: <wcs-router>’s basename has a setter (binding it threw), <wcs-defined>’s tags / mode / timeout are live, <wcs-throttle>’s leading works, <wcs-wakelock active manual> no longer takes the lock on upgrade, <wcs-ws> opens one socket, and an open DevTools State pane follows the page’s writes.

stateはカスタム要素のwc-bindableの入力をプロパティにだけ書く。3.xは入力のattributeヒントが名指す属性にも書いていたが、プロトコルはそのヒントをツールのための宣言と定めており、属性への反映はsetterの中で要素がすることだ。バインダーによる写しはそれとぶつかっていた: "false"と書かれたfalseは、属性の有無で読むI/Oノード — <wcs-wakelock active>、<wcs-camera keep-alive>、すべてのmanual — をオンにし、要素が自分で変えた属性は古いまま残った。wcstackの要素はどれもsetterで反映する。stateが属性を書くことに頼っていた自作の要素には、それを反映するsetterが要る。I/Oノードは、wc-bindable 0.10のプロデューサー向けの指針どおりにnullとundefinedを扱う: nullは入力の属性を取り除き(文書にある既定値)、undefinedは要素が最初に持っていた属性を戻し、どちらも文字列"null" / "undefined"にはならない — 3.xのString(value)は、<wcs-sse>・<wcs-ws>・<wcs-worker>にundefinedを開かせ、<wcs-storage>にキー"undefined"を読ませていた。@wcstack/stateはundefinedを決して書かない。書くのはReact 19、直接の代入、@wcstack/signalsのbindInputで、bindInputはいま、signalが別の値を持った後にだけそれを書く。修正も一緒に入る: <wcs-router>のbasenameにsetterが付き(バインドするとthrowしていた)、<wcs-defined>のtags / mode / timeoutは後からの変更が効き、<wcs-throttle>のleadingが動き、<wcs-wakelock active manual>がアップグレード時にロックを取ることはもう無く、<wcs-ws>はソケットを1つだけ開き、開いたDevToolsのStateペインはページの書き込みに追従する。

  • Property Only, No Attribute Mirror
  • null Clears, undefined Restores
  • bindInput Follows A2
  • Router, Throttle, Wakelock, ws Fixed

The Core Insight

The only contract is a path string

No hooks. No imports. No glue code.

フックなし。インポートなし。グルーコードなし。

In every existing framework, the component is where UI meets state. Even with external stores, you still write glue code inside the component to pull state in. State and UI always couple through JavaScript.

wcstack takes a different path. Literally. The only contract between UI and state is a path string — user.name, cart.items.*.subtotal, cart.total. The component's JavaScript doesn't contain a single line that references state. The HTML alone describes every data dependency — the same idea as a REST URL: a simple string contract, no shared code.

State   ← "user.name" →  UI          Path binds the two layers
Comp A  ← "cart.total" → Comp B      Mounted path crosses components
Loop    ← "items.*" →    Template    Wildcard abstracts the index

UIと状態を結ぶ唯一の契約はパス文字列。UIを作り直しても状態に触れなくていい。状態をリファクタリングしてもDOMに触れなくていい。HTMLを読めばすべてが分かる。

Constraints

Rules of the Game

This project follows five strict constraints. They're what make it interesting.

5つの厳格な制約。これが面白さの源泉。

1

Single CDN import

One <script> tag. That's it. No npm, no bundler, no config.

scriptタグ1つ。npm不要、バンドラー不要、設定不要。

2

Features as custom tags

Everything is a custom element. If it can't be expressed as <wcs-something>, it doesn't belong here.

すべてはカスタム要素。<wcs-something>で表現できなければ、ここには属さない。

3

Initial load = tag definitions only

The script just registers custom elements. No initialization code, no bootstrap ritual.

スクリプトはカスタム要素を登録するだけ。初期化コードもブートストラップ儀式も不要。

4

Respect HTML semantics

Expressions live in data-* attributes and text nodes — places HTML already allows extension. The DOM structure and semantics stay intact.

式はdata-*属性とテキストノードに配置 — HTMLが拡張を許可する場所のみ。DOM構造とセマンティクスはそのまま。

These rules sound simple. They're not. Respecting HTML semantics means you need to deeply understand where the spec allows extension — and where it doesn't. Building everything as custom tags means solving lifecycle, ordering, and communication within the Custom Elements spec. No dependencies means every algorithm is yours to write. And it all has to feel like it could be a browser built-in.

シンプルに聞こえるルールだが、実際は違う。HTMLセマンティクスを尊重するなら、仕様が拡張を許す場所と許さない場所を深く理解する必要がある。すべてをカスタムタグで構築するなら、Custom Elementsの仕様の中でライフサイクル・順序・通信を解決しなければならない。依存ゼロなら、あらゆるアルゴリズムを自分で書く。そしてそのすべてが「ブラウザ組み込みかもしれない」と感じさせなければならない。

Quick Start

One package, one script tag.

Pick only the scoped packages you need. Element packages ship an /auto entry.

必要なスコープ付きパッケージだけを選ぶ。要素パッケージは/autoエントリを持つ。

index.html CDN via esm.run 
<!-- Load the individual @wcstack/* packages your app uses -->
<script type="module" src="https://esm.run/@wcstack/router/auto"></script>
<script type="module" src="https://esm.run/@wcstack/fetch/auto"></script>
<script type="module" src="https://esm.run/@wcstack/autoloader/auto"></script>

<!-- Dev builds only: in-page DevTools overlay -->
<script type="module" src="https://esm.run/@wcstack/devtools/auto"></script>

<!-- State last: command-token emissions are not replayed -->
<script type="module" src="https://esm.run/@wcstack/state/auto"></script>

<!-- Or (v1.32.0+): the SPA core in ONE request — state + router + fetch +
     storage + autoloader pre-linked, one SRI hash covering all of it -->
<script type="module" src="https://esm.run/wcstack/auto"></script>
terminal Verify what you wrote 
# Check any HTML against the data-wcs contract. No install, no config.
# Exit code 0 means clean — iterate until it exits 0.
npx @wcstack/lint index.html

# Print the full authoring guide as plain text:
# binding syntax, filters, tokens, and the mistakes to avoid.
npm view wcstack readme

Each script registers its custom elements and does nothing else. No initialization, no bootstrap — tags activate when the browser parses them.

各スクリプトはカスタム要素を登録するだけ。初期化もブートストラップもなし — ブラウザがパースした時にタグが起動する。
