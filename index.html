What's New

Shipped in v3.0.0

3.0 reads a binding as written, or refuses it by name — and the core of @wcstack/state is split from its features. Forms that 2.x rounded off silently — a second #, a value after else:, an unterminated quote — now fail with [wcs/binding-syntax], and forms whose intent is clear are read the way they are written: done|eq(true) matches a boolean, join('; ') keeps its semicolon, an undefined caption removes alt instead of writing "undefined". There is no compatibility layer: 2.6 named every one of these forms as wcs/v3-migration, so upgrade to 2.6.1, clear those warnings, then move to 3.0 — the migration table lists each form with what to write instead. @wcstack/state and /auto still carry every feature, so a page that does not opt into the split entries loads as before. The changes are all in @wcstack/state and its tooling; every other package moves to 3.0.0 only to keep the lockstep version.

3.0はバインディングを書かれたとおりに読むか、名指しで拒む — そして@wcstack/stateのコアを機能から切り離す。2.xが黙って丸めていた書き方 — 2つ目の#、else:の後ろの値、閉じていない引用符 — は[wcs/binding-syntax]で失敗し、意図の明らかな書き方は書かれたとおりに読まれる: done|eq(true)は真偽値に一致し、join('; ')はセミコロンを保ち、undefinedのキャプションは"undefined"を書く代わりにaltを取り除く。互換層は無い: 2.6がこれらの書き方をすべてwcs/v3-migrationとして名指ししてきたので、2.6.1に上げて警告を消し、それから3.0へ移る — 書き方ごとの書き換え先は移行表にある。@wcstack/stateと/autoは今もすべての機能を載せているので、分割エントリを選ばないページは以前どおりに読み込まれる。変更はすべて@wcstack/stateとそのツールの中にあり、他のパッケージはロックステップのバージョンを揃えるためだけに3.0.0になる。

v3.0.0 wcs/binding-syntax

Refused by name

What if a malformed binding failed where you wrote it, instead of doing something plausible?

The 2.x parser answered broken input with a guess. value#ro#wo: kept ro and dropped the rest, else: x dropped x, a modifier on for / if / elseif / else / ... turned the keyword into a plain property binding, and an unterminated quote in filter arguments was closed for you. 3.0 rejects each of them with [wcs/binding-syntax] — write value#ro,wo:, else:, the bare keyword, the closed quote — and an empty filter (x|, x||y) moves to the same code. A filter given more or fewer arguments than it accepts now fails with [wcs/filter-arity] when the bindings are planned, instead of ignoring the extras. The other half is what used to break and now simply works: ; between bindings and | between filters split only outside quotes, so tags|join('; ') and parts|join(' | ') mean what they say, and resolved filters are cached by the structure of their arguments — slice('1,2') and slice(1,2) no longer share an entry. @wcstack/lint and the VS Code extension report wcs/binding-syntax at error with the canonical parser’s own judgement, so the editor and the page cannot disagree; the 2.6 wcs/v3-migration notice has done its job and is gone.

2.xのパーサは壊れた入力に推測で答えていた。value#ro#wo:はroを残して残りを捨て、else: xはxを捨て、for / if / elseif / else / ...に付いた修飾子はキーワードを普通のプロパティバインディングに変え、フィルタ引数の閉じていない引用符は勝手に閉じられた。3.0はそのどれも[wcs/binding-syntax]で拒む — value#ro,wo:、else:、キーワードだけ、閉じた引用符と書くこと — そして空のフィルタ(x|、x||y)も同じコードに移る。受け付ける数より多い・少ない引数を渡されたフィルタは、余りを無視する代わりに、バインディングの計画時に[wcs/filter-arity]で失敗する。もう半分は、これまで壊れていて、いまは素直に動くものだ: バインディング間の;とフィルタ間の|は引用符の外でだけ区切るので、tags|join('; ')もparts|join(' | ')も書いたとおりに動く。解決済みのフィルタは引数の構造でキャッシュされ、slice('1,2')とslice(1,2)が1つのエントリを共有することはもう無い。@wcstack/lintとVS Code拡張は正規のパーサ自身の判定でwcs/binding-syntaxをerrorとして報告するので、エディタとページの言い分が食い違うことはない。2.6のwcs/v3-migrationは役目を終えて取り除かれた。

  • No Silent Round-Offs
  • ; and | Inside Quotes
  • Filter Arity at Plan Time
  • Lint Uses the Same Parser
v3.0.0 done|eq(true)

Literals mean their type

What if eq(true) finally matched true?

A filter argument was always text in 2.x, so eq / ne compared a boolean or null value with the string "true" — done|eq(true) was always false — and defaults(null) fell back to the text "null". As of 3.0 an unquoted true, false, null or number is that value, and a quoted argument is a string: done|eq(true) matches true, eq('true') keeps the text comparison, eq(null) matches null, and defaults(0) gives the number 0 where defaults('0') gives "0". Numbers and strings compare as before, so a form value "1" still matches eq(1). Truthiness is JavaScript’s own in truthy / falsy / defaults, like boolean, so 0n is falsy now. And a modifier no longer changes the kind of binding: radio#ro: and checkbox#ro: stay radio / checkbox bindings that honour #ro, where 2.x made them a property named radio that did nothing.

2.xではフィルタ引数は常に文字列だったので、eq / neは真偽値やnullの値を文字列"true"と比べ — done|eq(true)は常にfalse — defaults(null)は文字列"null"を既定値にしていた。3.0からは、引用符の無いtrue・false・null・数値はその値そのもので、引用符付きの引数は文字列だ: done|eq(true)はtrueに一致し、eq('true')は文字列での比較を保ち、eq(null)はnullに一致し、defaults(0)は数値の0を、defaults('0')は"0"を返す。数値と文字列の比較は以前のままなので、フォームの値"1"は今もeq(1)に一致する。truthy / falsy / defaultsの真偽判定はbooleanと同じくJavaScript自身のものになり、0nは偽になった。そして修飾子はもうバインディングの種類を変えない: radio#ro:とcheckbox#ro:は#roを守るradio / checkboxバインディングのままだ。2.xではこれがradioという名前の、何もしないプロパティになっていた。

  • Unquoted Is Typed, Quoted Is Text
  • eq(true) Matches a Boolean
  • 0n Is Falsy
  • radio#ro: Stays a Radio Binding
v3.0.0 attr.alt: caption

No value means empty

What if a reused row could never show the previous row’s text?

In 2.x undefined meant “skip the write” everywhere — which is right for an element input, where the element keeps its own default, and wrong for text, where it kept whatever was showing: in a reused for row, the previous row’s text. An attribute got the string "undefined" or "null", and a style kept its old value. 3.0 treats the display surfaces — textContent / innerText / innerHTML, mustache text, attr.* and style.* — as places with no default worth keeping: undefined and null both mean “no value”, so the text becomes empty and the attribute or the style is removed. Element inputs, spread included, are unchanged: undefined still skips, null still clears. @wcstack/server renders with the same runtime, so server output follows the same rules — an undefined attribute is not emitted, which may move a snapshot test. If you returned undefined hoping to keep what was shown, keep that value yourself.

2.xではundefinedはどこでも「書き込みを飛ばす」だった — 要素が自分の既定値を保つ要素の入力には正しく、表示中のものを保ってしまうテキストには誤りだ: 使い回されたforの行では、それが前の行のテキストだった。属性には文字列"undefined"や"null"が入り、スタイルは古い値を保った。3.0は表示面 — textContent / innerText / innerHTML、mustacheのテキスト、attr.*、style.* — を、保つべき既定値の無い場所として扱う: undefinedもnullも「値なし」なので、テキストは空になり、属性やスタイルは取り除かれる。spreadを含む要素の入力は変わらない: undefinedは今も飛ばし、nullは今もクリアする。@wcstack/serverは同じランタイムで描画するので、サーバーの出力も同じ規則に従う — undefinedの属性は出力されず、スナップショットテストが動くことがある。表示中のものを保つつもりでundefinedを返していたなら、その値は自分で保つこと。

  • Empty Text, Not the Previous Row’s
  • Attributes Removed, Not Stringified
  • Element Inputs Unchanged
  • Server Output Follows
v3.0.0 installFeatures([...])

Only the features you use

What if a page that never folds a stream never loaded the code that does?

@wcstack/state/core holds the binding engine — data-wcs, for / if, path getters, events, command and event tokens. Everything else is a feature you add with installFeatures([...]): features/temporal ($watch, $scan, $streams), scopes (bind-component, mount=, DCC), recursion, ssr, formats (the formatting filters — the core answers only not), devtools and diagnostics (the development-time path warnings). The core alone is about 52 KB gzip, and every entry shares one core chunk. A missing feature does not fail quietly: a declaration that needs one throws [wcs/feature-not-installed], naming the entry to import. @wcstack/state/define gives defineState and the types with no runtime at all. Load the split form from jsDelivr’s plain, version-pinned /npm/ paths or through a bundler — never through esm.run, whose re-bundling would give every entry its own engine. @wcstack/state and /auto install every feature and stay the recommended way in: a page that uses them all is smaller as one file.

@wcstack/state/coreはバインディングエンジン — data-wcs、for / if、パスgetter、イベント、コマンドトークンとイベントトークン — を持つ。それ以外はすべてinstallFeatures([...])で足す機能だ: features/temporal($watch・$scan・$streams)、scopes(bind-component・mount=・DCC)、recursion、ssr、formats(書式フィルタ — コアが答えるのはnotだけ)、devtools、diagnostics(開発時のパス警告)。コアだけなら約52 KB gzipで、どのエントリも1つのコアチャンクを共有する。機能が欠けていても黙っては失敗しない: それを要る宣言は[wcs/feature-not-installed]をthrowし、importすべきエントリを名指しする。@wcstack/state/defineはランタイムを一切持たずにdefineStateと型を与える。分割形はjsDelivrの素の、バージョン固定した/npm/パスかバンドラから読み込み — esm.runからは決して読まない。その再バンドルは各エントリに別々のエンジンを持たせてしまう。@wcstack/stateと/autoはすべての機能を組み込み、今も推奨の入口だ: 全部を使うページなら1ファイルのほうが小さい。

  • Core About 52 KB gzip
  • Seven Feature Entries
  • A Missing Feature Throws by Name
  • Never Through esm.run
v3.0.0 state#ro: user

Writes that keep their word

What if #ro on a mount meant read-only, and a readonly proxy never wrote?

Several write paths in 2.x accepted a promise and ignored it. $resolve(path, indexes, undefined) was a read; in 3.0 the argument count decides, so it writes undefined, and $resolve(path, indexes) is the read. $resolve and $setAll — the ** broadcast included — wrote straight through a readonly proxy; they now throw This state is readonly. exactly as a direct assignment does. A component mounted with state#ro: user could write the host’s tree; now its writes throw [wcs/mount-readonly] and a two-way input inside it does not write back, while the host can still write the path. And a component’s own default for a key that an explicit partial mount covers (state.message: user.name) no longer hides the host value — the mount wins. What each scope runs is now one table: a root runs every declaration, a volume and a mounted component each run a stated subset, and nothing outside that subset is ignored silently.

2.xのいくつかの書き込み経路は、約束を受け取っておきながら無視していた。$resolve(path, indexes, undefined)は読みだった。3.0では引数の個数が決めるので、これはundefinedを書き、読みは$resolve(path, indexes)だ。$resolveと$setAllは — **のブロードキャストを含めて — readonlyのプロキシを素通りして書いていた。いまは直接の代入と同じくThis state is readonly.をthrowする。state#ro: userでマウントされたコンポーネントはホストの木に書けた。いまはその書き込みが[wcs/mount-readonly]をthrowし、中の双方向の入力も書き戻さない。ホストは今もそのパスに書ける。そして明示的な部分マウント(state.message: user.name)が覆うキーにコンポーネント自身が既定値を持っていても、もうホストの値を隠さない — マウントが勝つ。どのスコープが何を実行するかは1つの表になった: ルートはすべての宣言を実行し、ボリュームとマウントされたコンポーネントはそれぞれ決まった部分集合を実行し、その外にあるものは黙って無視されない。

  • The Argument Count Decides
  • Readonly Means Readonly
  • #ro Mounts Honoured
  • An Explicit Mount Wins
v3.0.0 10,000 rows

Faster rows, smaller file

What if a major release made the list you already have cheaper?

A plan row now renders straight from its row object, each row keeps one record, a list shares one binding session, and the cold row path stops allocating per node. Medians against 2.5.1 on the audit bench: creating 10,000 rows cold −18.7 %, appending 1,000 rows −15.9 %, clearing 10,000 rows −14.7 %; creating 1,000 rows warm is unchanged, and no measure regressed. The heap per row goes from 3.6 to 3.0 KB. The file the package name resolves to, dist/index.esm.js, is minified now: 321 KB → 79 KB gzip for a bundler that took it as it was — build from source with WCS_STATE_UNMINIFIED=1 for readable names in a profile. One number goes the other way, and it is stated: auto.min.js grows from 71.6 KB to about 77 KB gzip, for the feature receptacles and the fixes on this page. In DevTools, the State pane gains a Keyed selection section with the $eq / $eqPath / $eqIndex subscriptions per path, and a tracked badge on a path that fell back to re-evaluating every row.

The Core Insight

The only contract is a path string

No hooks. No imports. No glue code.

フックなし。インポートなし。グルーコードなし。

In every existing framework, the component is where UI meets state. Even with external stores, you still write glue code inside the component to pull state in. State and UI always couple through JavaScript.

wcstack takes a different path. Literally. The only contract between UI and state is a path string — user.name, cart.items.*.subtotal, cart.total. The component's JavaScript doesn't contain a single line that references state. The HTML alone describes every data dependency — the same idea as a REST URL: a simple string contract, no shared code.

State   ← "user.name" →  UI          Path binds the two layers
Comp A  ← "cart.total" → Comp B      Mounted path crosses components
Loop    ← "items.*" →    Template    Wildcard abstracts the index

UIと状態を結ぶ唯一の契約はパス文字列。UIを作り直しても状態に触れなくていい。状態をリファクタリングしてもDOMに触れなくていい。HTMLを読めばすべてが分かる。

See it in action

Code that reads like HTML

Because it is HTML.

HTMLのように読める。なぜなら、HTMLだから。

index.html State 
<wcs-state>
  <script type="module">
    export default {
      taxRate: 0.1,
      cart: {
        items: [
          { name: "Widget", price: 500, quantity: 2 },
          { name: "Gadget", price: 1200, quantity: 1 }
        ]
      },
      removeItem(event, index) {
        this["cart.items"] = this["cart.items"].toSpliced(index, 1);
      },
      get "cart.items.*.subtotal"() {
        return this["cart.items.*.price"] * this["cart.items.*.quantity"];
      },
      get "cart.total"() {
        return this.$getAll("cart.items.*.subtotal", [])
          .reduce((a, b) => a + b, 0);
      },
      get "cart.grandTotal"() {
        return this["cart.total"] * (1 + this.taxRate);
      }
    };
  </script>
</wcs-state>

<template data-wcs="for: cart.items">
  <div>
    {{ .name }} &times;
    <input type="number" data-wcs="value: .quantity">
    = <span data-wcs="textContent: .subtotal|locale"></span>
    <button data-wcs="onclick: removeItem">Delete</button>
  </div>
</template>
<p>Grand Total: <span data-wcs="textContent: cart.grandTotal|locale(ja-JP)"></span></p>

Constraints

Rules of the Game

This project follows five strict constraints. They're what make it interesting.

5つの厳格な制約。これが面白さの源泉。

1

Single CDN import

One <script> tag. That's it. No npm, no bundler, no config.

scriptタグ1つ。npm不要、バンドラー不要、設定不要。

2

Features as custom tags

Everything is a custom element. If it can't be expressed as <wcs-something>, it doesn't belong here.

すべてはカスタム要素。<wcs-something>で表現できなければ、ここには属さない。

3

Initial load = tag definitions only

The script just registers custom elements. No initialization code, no bootstrap ritual.

スクリプトはカスタム要素を登録するだけ。初期化コードもブートストラップ儀式も不要。

4

Respect HTML semantics

Expressions live in data-* attributes and text nodes — places HTML already allows extension. The DOM structure and semantics stay intact.

式はdata-*属性とテキストノードに配置 — HTMLが拡張を許可する場所のみ。DOM構造とセマンティクスはそのまま。

5

Latest ECMAScript

We actively adopt cutting-edge JS features. No transpiling to ES5. This is the future, after all.

最新のJS機能を積極採用。ES5へのトランスパイルなし。未来のプロジェクトだから。

These rules sound simple. They're not. Respecting HTML semantics means you need to deeply understand where the spec allows extension — and where it doesn't. Building everything as custom tags means solving lifecycle, ordering, and communication within the Custom Elements spec. No dependencies means every algorithm is yours to write. And it all has to feel like it could be a browser built-in.

シンプルに聞こえるルールだが、実際は違う。HTMLセマンティクスを尊重するなら、仕様が拡張を許す場所と許さない場所を深く理解する必要がある。すべてをカスタムタグで構築するなら、Custom Elementsの仕様の中でライフサイクル・順序・通信を解決しなければならない。依存ゼロなら、あらゆるアルゴリズムを自分で書く。そしてそのすべてが「ブラウザ組み込みかもしれない」と感じさせなければならない。

One package, one script tag.
