v2.1.0 focus="heading"

The focus reset, actually reset

What if opting into an accessibility policy could never make things worse?

It could, and now it cannot. Two holes closed. The gate did not match what ran: any focus= attribute made the router tell the Navigation API focusReset: "manual", but only the exact value "heading" made the policy act — so focus="" or a typo switched off the browser’s own reset and put nothing in its place. Now only "heading" activates, and anything else falls back to the browser. A route without a heading stranded focus: it stayed on the element you clicked, and a persistent nav <wcs-link> is the common case — leaving a screen reader on the previous screen. The router now reproduces the spec-default reset itself: first [autofocus], else <body>. Hidden headings are skipped (focusing them was a no-op with the same result), and <wcs-link> mirrors lang / dir to its anchor so a multilingual nav announces in the right language.

悪化させうる状態だった。もうそうはならない。塞いだ穴は2つ。ゲートが実装と食い違っていた: どのfocus=属性でもrouterはNavigation APIにfocusReset: "manual"を渡すのに、ポリシーが動くのは値がちょうど"heading"のときだけ — つまりfocus=""やタイプミスは、ブラウザ自身のリセットを切った上で代わりに何もしなかった。いまは"heading"だけが有効化し、それ以外はブラウザ既定に戻る。見出しの無いルートはフォーカスを取り残した: クリックした要素に留まり続け、永続ナビの<wcs-link>が典型だった — スクリーンリーダーは前の画面に置き去りになる。routerはいまspec既定のリセットを自前で再現する: まず[autofocus]、無ければ<body>。非表示の見出しはスキップされ(フォーカスしても無効で同じ結果だった)、<wcs-link>はlang / dirをアンカーに転写するので、多言語ナビが正しい言語で読み上げられる。

  • Exact Value or Browser Default
  • No Heading, Still Reset
  • Hidden Headings Skipped
  • lang / dir Reach the Anchor
v2.1.0 $updatedCallback

Private keys stay private

What if privacy held all the way to the last channel?

A mounted component’s own data keys are private to that mount instance (rule R1) — they live in a separate address space carrying a marker segment, users.*.#m3.editing, so they cannot collide with the tree. But those addresses were still being delivered to the root’s $updatedCallback, where they are worse than useless: the #m<id> vocabulary means nothing outside the scope, and the id changes on every re-initialization, so no author could act on one. They are now filtered out at the delivery boundary, for both the root and a volume’s relative callback. In the same pass, IStateElement.name and State.get name() were removed — dead surface that always returned "default" once the name dimension was gone.

マウントされたコンポーネント自身のデータキーは、そのマウントインスタンスに私有だ(規則R1) — マーカーセグメントを含む別のアドレス空間users.*.#m3.editingに載るので、木とは衝突しない。だがそのアドレスがルートの$updatedCallbackには届いてしまっていた。そこでは無意味を通り越して有害で、#m<id>という語彙はスコープの外では意味を持たず、idは再初期化のたびに変わるので、作者は何も判断できない。いまは配送の境界で除外される。ルートでも、ボリュームの相対コールバックでも同じ。同じ整理でIStateElement.nameとState.get name()が削除された — 名前の次元が消えた後は常に"default"を返すだけの死んだ表面だった。

  • Marker Paths Filtered Out
  • Root and Volume Alike
  • Unstable ids Never Escape
  • Dead name Surface Removed
v2.1.0 overlays()

Devtools can see the mount

What if the invisible half of the tree had a window?

Private keys and component getters live in the overlay address space, which means they never appear in keys() or read() — correct for the runtime, but it left the devtools showing only half of what a mounted page holds. The State pane gains an Overlays section under the selected tree’s key list: one entry per mount record, with its marker, mount table, delta and private/getter keys. The protocol member shipped in v2.0.0 unconsumed; this is the UI catching up, and it is called optionally — a runtime without overlays() hides the section entirely, and an empty array renders no heading. Alongside it, state:watch-fired and state:token-emit now carry the firing tree, so measurements stay attributed per tree on a page where several trees declare the same watch path.

私有キーとコンポーネントのgetterはオーバーレイのアドレス空間に居る。つまりkeys()にもread()にも現れない — ランタイムとしては正しいが、devtoolsはマウントされたページの半分しか映せていなかった。Stateペインに、選択中の木のキー一覧の下へOverlaysセクションが加わる。マウント記録ごとに1エントリ、マーカー・マウント表・デルタ・私有/getterキーつき。プロトコルのメンバー自体はv2.0.0で未消費のまま出ていた。これはUIが追いついた形で、呼び出しはoptional — overlays()を持たないランタイムではセクションごと隠れ、空配列なら見出しも出ない。あわせてstate:watch-firedとstate:token-emitが発火した木を運ぶようになり、同じwatchパスを複数の木が宣言するページでも計測が木ごとに帰属する。

  • One Entry Per Mount Record
  • The Half keys() Never Showed
  • Optional, Degrades Silently
  • Measurements Per Tree

The Core Insight

The only contract is a path string

No hooks. No imports. No glue code.

フックなし。インポートなし。グルーコードなし。

In every existing framework, the component is where UI meets state. Even with external stores, you still write glue code inside the component to pull state in. State and UI always couple through JavaScript.

wcstack takes a different path. Literally. The only contract between UI and state is a path string — user.name, cart.items.*.subtotal, cart.total. The component's JavaScript doesn't contain a single line that references state. The HTML alone describes every data dependency — the same idea as a REST URL: a simple string contract, no shared code.

State   ← "user.name" →  UI          Path binds the two layers
Comp A  ← "cart.total" → Comp B      Mounted path crosses components
Loop    ← "items.*" →    Template    Wildcard abstracts the index

UIと状態を結ぶ唯一の契約はパス文字列。UIを作り直しても状態に触れなくていい。状態をリファクタリングしてもDOMに触れなくていい。HTMLを読めばすべてが分かる。

One protocol behind them all: wc-bindable

Every I/O node exposes a static manifest — observable properties, settable inputs, invocable commands — so any binding core can discover and wire it generically. Since v1.24.0 each observable also declares its semantics — state, event, or handle — so a generic adapter can tell a current value from an occurrence. <wcs-state> and @wcstack/signals speak it natively; thin adapters connect React, Vue, Svelte, and Solid.

index.html State 
<wcs-state>
  <script type="module">
    export default {
      taxRate: 0.1,
      cart: {
        items: [
          { name: "Widget", price: 500, quantity: 2 },
          { name: "Gadget", price: 1200, quantity: 1 }
        ]
      },
      removeItem(event, index) {
        this["cart.items"] = this["cart.items"].toSpliced(index, 1);
      },
      get "cart.items.*.subtotal"() {
        return this["cart.items.*.price"] * this["cart.items.*.quantity"];
      },
      get "cart.total"() {
        return this.$getAll("cart.items.*.subtotal", [])
          .reduce((a, b) => a + b, 0);
      },
      get "cart.grandTotal"() {
        return this["cart.total"] * (1 + this.taxRate);
      }
    };
  </script>
</wcs-state>

<template data-wcs="for: cart.items">
  <div>
    {{ .name }} &times;
    <input type="number" data-wcs="value: .quantity">
    = <span data-wcs="textContent: .subtotal|locale"></span>
    <button data-wcs="onclick: removeItem">Delete</button>
  </div>
</template>
<p>Grand Total: <span data-wcs="textContent: cart.grandTotal|locale(ja-JP)"></span></p>

<!-- Filters transform VALUES only. An event handler never takes a filter.
     BAD:  data-wcs="onkeydown: addTodo|enter"   <- no such filter exists
     GOOD: data-wcs="onkeydown: addTodo"         <- inspect event.key in the method
     Mutating state in place is not reactive either.
     BAD:  this.cart.items.push(x)
     GOOD: this["cart.items"] = [...this["cart.items"], x] -->

Constraints

Rules of the Game

This project follows five strict constraints. They're what make it interesting.

5つの厳格な制約。これが面白さの源泉。

1

Single CDN import

One <script> tag. That's it. No npm, no bundler, no config.

scriptタグ1つ。npm不要、バンドラー不要、設定不要。

2

Features as custom tags

Everything is a custom element. If it can't be expressed as <wcs-something>, it doesn't belong here.

すべてはカスタム要素。<wcs-something>で表現できなければ、ここには属さない。

3

Initial load = tag definitions only

The script just registers custom elements. No initialization code, no bootstrap ritual.

スクリプトはカスタム要素を登録するだけ。初期化コードもブートストラップ儀式も不要。

4

Respect HTML semantics

Expressions live in data-* attributes and text nodes — places HTML already allows extension. The DOM structure and semantics stay intact.

式はdata-*属性とテキストノードに配置 — HTMLが拡張を許可する場所のみ。DOM構造とセマンティクスはそのまま。

5

Latest ECMAScript

We actively adopt cutting-edge JS features. No transpiling to ES5. This is the future, after all.

最新のJS機能を積極採用。ES5へのトランスパイルなし。未来のプロジェクトだから。

These rules sound simple. They're not. Respecting HTML semantics means you need to deeply understand where the spec allows extension — and where it doesn't. Building everything as custom tags means solving lifecycle, ordering, and communication within the Custom Elements spec. No dependencies means every algorithm is yours to write. And it all has to feel like it could be a browser built-in.

シンプルに聞こえるルールだが、実際は違う。HTMLセマンティクスを尊重するなら、仕様が拡張を許す場所と許さない場所を深く理解する必要がある。すべてをカスタムタグで構築するなら、Custom Elementsの仕様の中でライフサイクル・順序・通信を解決しなければならない。依存ゼロなら、あらゆるアルゴリズムを自分で書く。そしてそのすべてが「ブラウザ組み込みかもしれない」と感じさせなければならない。
