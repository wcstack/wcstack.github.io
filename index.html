v2.5.0 setInitialState()

The page follows the new state

What if handing over a whole new state re-drew the page?

setInitialState(next) on an already-initialized element swapped the state in and reads returned its values — but no established binding was ever applied again, so the page went on showing the previous state until some dependent path happened to be written. The re-set now re-applies every established binding to the new state before it returns: scalars, getters, row getters, for and if alike. Structural bindings go first, outer before inner, so a binding inside an if that the re-set closes is detached before anything reads it, rather than reporting a failure that is not one. A binding the new state cannot serve is reported as a failed apply — console.error, or the new state’s $errorCallback — instead of being left showing the old text. A detached element re-applies when it reconnects, and a view-transition arbiter on the page receives the re-apply exactly as it receives an update. On ≤2.4 the answer was to write the individual paths one by one; now you can hand over the object.

初期化済みの要素へのsetInitialState(next)はstateを差し替え、読みは新しい値を返した — が、確立済みのバインディングが再び適用されることは無かった。だからページは、依存するパスがたまたま書かれるまで前のstateを映し続けた。再セットはいま戻る前に、確立済みのバインディングをすべて新しいstateへ再適用する: スカラーもgetterも行getterも、forもifも同じように。構造バインディングが先で、外側から内側へ。だから再セットが閉じるifの中のバインディングは、誰かが読む前に切り離される — 失敗でないものを失敗として報告しない。新しいstateが応えられないバインディングは適用の失敗として報告され(console.error、または新しいstateの$errorCallback)、古い文字列を表示したまま放置されない。外れている要素は再接続時に再適用し、ページ上のview-transition arbiterは更新を受け取るのとまったく同じ形で再適用を受け取る。≤2.4での答えは個々のパスを1つずつ書くことだった。いまはオブジェクトごと渡せる。

  • Re-applied Before It Returns
  • Structural First, Outer to Inner
  • A Failed Apply Is Reported
  • Re-applies on Reconnect
v2.5.0 array identity

A re-set is not a write

What if replacing the whole state fired nothing at all?

A re-set replaces the state; it does not write to it. No $watch handler, no $scan fold, no $streams restart and no $updatedCallback — the new declarations simply arm themselves. One rule has to be honoured in return: lists are matched by array identity, so put a new array in the object you hand over whenever a list’s length changed. Pushing into the array in place and re-setting with the same instance is not supported — the row diff sees the array it already rendered, the added or removed rows never reach the page, and nothing is reported. The “report each path once” ledger behind wcs/binding-path-missing now belongs to one state generation too: a path the new state spells differently (user.nmae where the first had user.name) is reported again instead of staying silent on the record the first generation left, while a $watch path the new state no longer declares is not reported at all. What a re-set still refuses is unchanged — a tree that already has grafted volumes or mounted components, and an element that failed to initialize.

再セットはstateを置き換えるのであって、書き込むのではない。$watchハンドラも$scanのfoldも$streamsの再起動も$updatedCallbackも走らない — 新しい宣言は自分で立ち上がるだけだ。代わりに守るべき規則が1つある: リストは配列の同一性で照合されるので、リストの長さが変わったなら渡すオブジェクトには新しい配列を入れること。その場でpushした同じインスタンスで再セットするのはサポート外だ — 行の差分はすでに描画済みの配列を見るので、増えた行も減った行もページに届かず、何も報告されない。wcs/binding-path-missingの裏にある「パスごとに1回だけ報告する」台帳も、いまはstateの世代ごとに属する: 新しいstateで綴りが違うパス(最初はuser.nameだったところのuser.nmae)は、前の世代が残した記録に黙らされずにもう一度報告され、新しいstateがもう宣言しない$watchのパスは報告されない。再セットが拒むものは変わらない — すでにボリュームやマウント済みコンポーネントが接ぎ木された木と、初期化に失敗した要素。

  • No $watch, No $scan, No $updatedCallback
  • Lists Match by Array Identity
  • One Ledger Per Generation
  • Volumes and Mounts Still Refused
v2.5.0 mount="cart"

A slot you can have back

What if a volume that never grafted let go of its mount path?

A volume that settles without grafting — it failed to load, its root failed and orphaned it, or it was detached while still loading or waiting for that root — used to keep its mount path reserved for as long as the root node lived. The slot ledger had no way to release one, so a replacement element on the same path was rejected with Volume slot "…" is already mounted on this tree., an error nothing awaiting the page ever saw, and reloading was the only recovery. A volume now releases its slot when it settles without grafting, and takes it back when it is re-attached to the same root or otherwise just before it grafts; if another volume took the slot meanwhile, that is reported and the graft is skipped. A grafted volume keeps its slot even while detached, and a release only removes that element’s own reservation, so removing a dead volume never frees a slot another one holds. Reads under a released path still resolve to undefined. The other half of the same story: setInitialState() on a loaded volume element now throws. The graft copies a volume’s data into the root tree once, so re-setting the element only ever changed that element’s own reads — write the paths under the mount path on the root instead.

接ぎ木しないまま決着したボリューム — 読み込みに失敗した、ルートが失敗して孤立した、読み込み中やルート待ちのまま外された — は、そのルートノードが生きているかぎりマウントパスを予約したままだった。スロットの台帳には解放する手段が無かったので、同じパスへの代わりの要素はVolume slot "…" is already mounted on this tree.で拒否された — ページを待っている誰にも見えないエラーだ — 復旧はリロードしかなかった。ボリュームはいま接ぎ木せずに決着したらスロットを解放する。そして同じルートへ再接続されたとき、あるいは接ぎ木の直前に取り戻す。その間に別のボリュームがスロットを取っていれば、それを報告して接ぎ木は行わない。接ぎ木済みのボリュームは外れていてもスロットを保ち、解放はその要素自身の予約だけを外すので、死んだボリュームを取り除いても他のボリュームが持つスロットは決して空かない。解放されたパスの下の読みは従来どおりundefinedになる。同じ話のもう半分: 読み込み済みのボリューム要素へのsetInitialState()はいまthrowする。接ぎ木はボリュームのデータをルートの木へ一度だけコピーするので、要素の再セットはその要素自身の読みしか変えなかった — 代わりにルート側でマウントパス配下のパスに書くこと。

  • Released When It Settles
  • Taken Back Before the Graft
  • Only Its Own Reservation
  • A Volume Re-set Throws
v2.5.0 enable-ssr

A hydrated row that follows

What if a server-rendered row updated like any other?

Hydration registered the bindings inside server-rendered blocks without applying them — it applied only the bindings outside those blocks. A getter records its dependencies the moment it is evaluated, so a row getter that was never evaluated recorded none: textContent: items.*.double kept the server-rendered text when items.0.n changed, while an aggregate outside the rows updated normally, and nothing said so. Hydration now applies the bindings inside for rows and if blocks once, as it already did for the ones outside them. The text on screen does not change — the values come from the same state — only the dependency edges appear. Structural and event bindings, bindings on comment nodes, and index bindings ($1, $2, which depend on no state) are deliberately left as the server rendered them. The remaining gaps are named rather than papered over: the inner rows of a nested for are left unapplied instead of reporting a failure on every hydration, and mustache text inside rows, a for inside an if and bind-component children inside rows are separate gaps, unchanged.

ハイドレーションはサーバーが描いたブロックの中のバインディングを登録しながら、適用はしていなかった — 適用されたのはブロックの外のバインディングだけだ。getterが依存を記録するのは評価された瞬間なので、一度も評価されない行getterは何も記録しない: items.0.nが変わってもtextContent: items.*.doubleはサーバーが描いた文字列のままで、行の外の集計値はふつうに更新され、そのことを告げるものは何も無かった。ハイドレーションはいまforの行とifブロックの中のバインディングを一度だけ適用する — 外側にはすでにそうしていたとおりに。画面の文字は変わらない(値は同じstateから来る)。現れるのは依存の辺だけだ。構造バインディングとイベントバインディング、コメントノード上のバインディング、そしてインデックスバインディング($1・$2。stateに依存しない)は、意図してサーバーが描いたままにされる。残る穴は塗り隠さずに名指しされている: ネストしたforの内側の行は、ハイドレーションのたびに失敗を報告するのではなく未適用のまま残される。行の中のmustacheテキスト、ifの中のfor、行の中のbind-componentの子は別の穴で、こちらは変わらない。

  • Applied Once, Inside the Block
  • Same Text, Real Dependencies
  • Index Bindings Left Alone
  • Nested Rows Still a Gap
v2.5.0 items.0 = c

Blocks that travel with their values

What if swapping two rows by writing them kept everything in step?

this.$resolve("items.*", [0], b) and this["items.0"] = c are element writes, not array mutations, and they were legitimate all along — but the list was never re-rendered. The runtime moved each row’s identity with its value while pinning the written value to the row that used to sit at that position: the blocks stayed put with their contents rewritten, items.0.name read the other row, a row’s $1 disagreed with the text beside it, a write landed on the other row, and a later array replacement left the page out of step with the array. All of it silent. A completed swap is now re-rendered as a replacement of the order before the writes, so the row blocks move with their values — and with them a row’s $1 and the DOM state the bindings do not own, such as text typed into an unbound input. Writing a value that was not in the list replaces that row in place: its block stays where it is, an input being edited in it keeps focus, and its row getters show the new row. Equal primitives cannot be told apart, so writes that end in a reordering of the same values count as a swap. The completed swap is queued render-only, so $watch lands neither on items nor on items.* for a row that merely moved — a replacement does land, with prev = the row it replaced.

this.$resolve("items.*", [0], b)とthis["items.0"] = cは配列の破壊的変更ではなく要素への書き込みで、はじめから正当な操作だった — が、リストは再描画されなかった。ランタイムは行の同一性を値とともに動かしながら、書かれた値をその位置に元々いた行に貼り付けていた: ブロックはその場に留まって中身だけ書き換えられ、items.0.nameは別の行を読み、行の$1は隣の文字と食い違い、書き込みは別の行に着地し、後から配列を差し替えるとページは配列とずれたままになった。どれも無言で。完了したswapはいま、書き込み前の順序に対する置き換えとして再描画される。だから行のブロックは値とともに動く — 行の$1も、バインディングが所有していないDOM状態(バインドしていない入力欄に打ち込んだ文字など)も一緒に。リストに無かった値を書くとその行はその場で置き換わる: ブロックは動かず、編集中の入力欄はフォーカスを保ち、その行のgetterは新しい行を映す。等しいプリミティブは区別できないので、同じ値の並べ替えに終わる書き込みはswapとして扱われる。完了したswapは描画のみでキューされるため、ただ移動しただけの行について$watchはitemsにもitems.*にも着地しない — 置き換えなら着地し、prevは置き換えられた行になる。

  • The Block Moves With the Value
  • $1 Follows the Row
  • A New Value Replaces In Place
  • A Move Lands Nothing
v2.5.0 one batch

Written, then replaced

What if a row could be written and replaced in the same batch?

s["items.0.n"] = 5; s.items = [{ n: 9 }, s.items[1]] — a write into a row, then a new array, in one batch. The first write queued that row’s binding; the binding was applied for the row the second write had already removed; and the list then reused that row’s pooled content for the new row and skipped the binding as already applied. The page showed 5 while the state held 9, with nothing to point at. A row is now torn down when the list reuses its block in place, so the new row’s binding is applied to the new row. Two neighbours came with it: a replaced row keeps its block and its prev when an element write replaces it, and a replaced row’s nested-list ledgers are no longer cleared out from under it — the list-clearing shortcut used to wipe a sibling anchor along the way. What remains is one recorded gap, with the page and the state both correct: $watch / $scan on a path inside a replaced row’s nested list does not land for that row.

s["items.0.n"] = 5; s.items = [{ n: 9 }, s.items[1]] — 行への書き込みと新しい配列が、1つのバッチに同居する。最初の書き込みはその行のバインディングをキューに積み、そのバインディングは2つ目の書き込みがすでに取り除いた行に対して適用され、リストはその行のプールされた内容を新しい行に再利用して、バインディングを適用済みとして飛ばした。ページは5を出し、stateは9を持ち、指させるものは何も無かった。リストがブロックをその場で再利用するとき、行はいま解体される。だから新しい行のバインディングは新しい行に適用される。隣接する2件も一緒に直った: 要素への書き込みが行を置き換えるとき、置き換えられた行はブロックとprevを保つ。そして置き換えられた行のネストしたリストの台帳が足元から消されることもなくなった — リストを空にする近道が、ついでに兄弟のアンカーまで拭き取っていた。残るのは記録済みの穴が1つ、ページもstateも正しいままでの話だ: 置き換えられた行のネストしたリストの中のパスへの$watch / $scanは、その行について着地しない。

  • Pooled Content Torn Down
  • The New Row’s Binding Applies
  • Nested Ledgers Survive
  • Nested-list $watch Still a Gap

The Core Insight

The only contract is a path string

No hooks. No imports. No glue code.

フックなし。インポートなし。グルーコードなし。

In every existing framework, the component is where UI meets state. Even with external stores, you still write glue code inside the component to pull state in. State and UI always couple through JavaScript.

wcstack takes a different path. Literally. The only contract between UI and state is a path string — user.name, cart.items.*.subtotal, cart.total. The component's JavaScript doesn't contain a single line that references state. The HTML alone describes every data dependency — the same idea as a REST URL: a simple string contract, no shared code.

State   ← "user.name" →  UI          Path binds the two layers
Comp A  ← "cart.total" → Comp B      Mounted path crosses components
Loop    ← "items.*" →    Template    Wildcard abstracts the index

UIと状態を結ぶ唯一の契約はパス文字列。UIを作り直しても状態に触れなくていい。状態をリファクタリングしてもDOMに触れなくていい。HTMLを読めばすべてが分かる。

One protocol behind them all: wc-bindable

Every I/O node exposes a static manifest — observable properties, settable inputs, invocable commands — so any binding core can discover and wire it generically. Code that reads like HTML

Because it is HTML.

HTMLのように読める。なぜなら、HTMLだから。

index.html State 
<wcs-state>
  <script type="module">
    export default {
      taxRate: 0.1,
      cart: {
        items: [
          { name: "Widget", price: 500, quantity: 2 },
          { name: "Gadget", price: 1200, quantity: 1 }
        ]
      },
      removeItem(event, index) {
        this["cart.items"] = this["cart.items"].toSpliced(index, 1);
      },
      get "cart.items.*.subtotal"() {
        return this["cart.items.*.price"] * this["cart.items.*.quantity"];
      },
      get "cart.total"() {
        return this.$getAll("cart.items.*.subtotal", [])
          .reduce((a, b) => a + b, 0);
      },
      get "cart.grandTotal"() {
        return this["cart.total"] * (1 + this.taxRate);
      }
    };
  </script>

Constraints

Rules of the Game

This project follows five strict constraints. They're what make it interesting.

5つの厳格な制約。これが面白さの源泉。

1

Single CDN import

One <script> tag. That's it. No npm, no bundler, no config.

scriptタグ1つ。npm不要、バンドラー不要、設定不要。

2

Features as custom tags

Everything is a custom element. If it can't be expressed as <wcs-something>, it doesn't belong here.

すべてはカスタム要素。<wcs-something>で表現できなければ、ここには属さない。

3

Initial load = tag definitions only

The script just registers custom elements. No initialization code, no bootstrap ritual.

スクリプトはカスタム要素を登録するだけ。初期化コードもブートストラップ儀式も不要。

4

Respect HTML semantics

Expressions live in data-* attributes and text nodes — places HTML already allows extension. The DOM structure and semantics stay intact.

式はdata-*属性とテキストノードに配置 — HTMLが拡張を許可する場所のみ。DOM構造とセマンティクスはそのまま。

5

Latest ECMAScript

We actively adopt cutting-edge JS features. No transpiling to ES5. This is the future, after all.

最新のJS機能を積極採用。ES5へのトランスパイルなし。未来のプロジェクトだから。

These rules sound simple. They're not. Respecting HTML semantics means you need to deeply understand where the spec allows extension — and where it doesn't. Building everything as custom tags means solving lifecycle, ordering, and communication within the Custom Elements spec. No dependencies means every algorithm is yours to write. And it all has to feel like it could be a browser built-in.

シンプルに聞こえるルールだが、実際は違う。HTMLセマンティクスを尊重するなら、仕様が拡張を許す場所と許さない場所を深く理解する必要がある。すべてをカスタムタグで構築するなら、Custom Elementsの仕様の中でライフサイクル・順序・通信を解決しなければならない。依存ゼロなら、あらゆるアルゴリズムを自分で書く。そしてそのすべてが「ブラウザ組み込みかもしれない」と感じさせなければならない。
