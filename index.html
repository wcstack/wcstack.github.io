v2.2.0 guard → data

The guard was already the loader

What if a route could load its data without a new lifecycle phase?

A guard function was already the one asynchronous step that runs before the route content is swapped in. v2.2.0 lets it return more than a boolean. Return an object and the router enters the route and commits it as the new output-only <wcs-router>.data member (wcs-router:data-changed, fired first in the commit order) — so the page never shows the new route with empty content, and a <wcs-view-transition> animates real content instead of a blank frame. Return a non-empty string and the navigation is cancelled and redirected there, a dynamic target that wins over the static guard= attribute. The function also receives a third argument, a frozen { params, typedParams, searchParams, routeName } snapshot of the match being entered, so fetch(`/api/users/${typedParams.id}`) needs no URL parsing. Every falsy return still cancels, so existing guards are untouched. On a nested chain each guard may return an object; they shallow-merge parent → child, and data is null on a navigation that loads nothing.

ガード関数はもともと、ルートの内容が差し替わる前に走る唯一の非同期ステップだった。v2.2.0はそこから真偽値以外も返せるようにする。オブジェクトを返せばrouterはルートに入り、それを新設の出力専用メンバー<wcs-router>.dataとしてコミットする(wcs-router:data-changed、コミット順の先頭で発火) — だからページが空の内容で新ルートを見せる瞬間はなく、<wcs-view-transition>は空白のフレームではなく実際の内容をアニメーションする。空でない文字列を返せばナビゲーションは取り消されそこへリダイレクトされる。静的なguard=属性に勝つ動的な行き先だ。関数は第3引数として、入ろうとしているマッチの凍結スナップショット{ params, typedParams, searchParams, routeName }も受け取るので、fetch(`/api/users/${typedParams.id}`)にURL解析は要らない。falsyな戻り値は今までどおり取り消しなので、既存のガードは無傷。ネストしたチェーンでは各ガードがオブジェクトを返してよく、親→子でshallow-mergeされる。何も読み込まないナビゲーションではdataはnull。

  • Object In, Route Entered
  • String In, Redirected
  • The Match, Frozen
  • Falsy Still Cancels
v2.2.0 state: path

A component’s getters, readable from outside

What if a mounted component could answer questions the tree cannot?

A component mounted at user has always read the tree through its mount point. For getters the direction is now two-way: a read of a key the tree does not have is answered by the getter of the component mounted there. <span data-wcs="textContent: user.display"> renders the component’s get display(); a key the tree does have still wins, with a one-time wcs/mount-export-shadowed warning, and private keys and methods are never visible. Row mounts export per row, so $getAll("users.*.display") and text: .display inside the same for read each row component’s getter, and dependencies flow through — change user.name and everything that read user.display re-renders. Writing to an exported key runs the accessor’s setter or throws, so the tree never grows a key that would hide the getter. The payoff is self-recursive components: a <tree-node> that renders <tree-node data-wcs="state: ."> for each child can define get total() over this.$getAll("children.*.total") — each level closes over one level, and the ledger resolves the recursion. Paths cannot express recursion; the recursion lives in the DOM, and the paths are its unrolled form. The parent evaluates before the child registers, so the first read may see undefined: write (x ?? 0).

userにマウントされたコンポーネントは、ずっとマウント点を通して木を読んできた。getterについては、いまやその向きが双方向になる: 木に無いキーの読みは、そこにマウントされたコンポーネントのgetterが答える。<span data-wcs="textContent: user.display">はコンポーネントのget display()を描画する。木にあるキーは引き続き木が勝ち、wcs/mount-export-shadowedが一度だけ警告する。私有キーとメソッドは決して見えない。行マウントは行ごとにエクスポートするので、同じforの中の$getAll("users.*.display")とtext: .displayは各行コンポーネントのgetterを読み、依存は貫通する — user.nameを変えればuser.displayを読んだものすべてが再描画される。エクスポートされたキーへの書き込みはアクセサのsetterを走らせるか、無ければthrowする。getterを隠すキーが木に生えることはない。見返りは自己再帰コンポーネントだ: 子ごとに<tree-node data-wcs="state: .">を描く<tree-node>が、this.$getAll("children.*.total")の上にget total()を定義できる — 各階層の式は1階層分だけを閉じ込め、再帰は台帳が解決する。パスは再帰を表現できない。再帰はDOMに宿り、パスはその展開形だ。親は子が登録するより先に評価されるので、最初の読みはundefinedになりうる: (x ?? 0)と書くこと。

  • Tree Key Wins, Warns Once
  • Per Row, Dependencies Flow
  • Setter or Throw, Never Shadow
  • Recursion Lives in the DOM
v2.2.0 $errorCallback

An error boundary, in the page

What if a failing binding reported to the page instead of the console?

A binding whose application throws — a path getter or a filter threw, a structural directive failed — was already isolated: the rest of the batch still applies, nothing is rolled back, and the failure went to console.error and to DevTools. Declare $errorCallback(error, info) on the root state and the report comes to you instead. info is { path, bindingType, node }, with the path as written in data-wcs, wildcards intact; this is the writable state proxy, so the usual shape is to write the message into state and render it like anything else. The hook runs once per failed binding after $updatedCallback, is not awaited, and its own exceptions are isolated, so it cannot take the drain down with it. DevTools keeps receiving state:binding-apply-error either way. Root-only — a volume declaring it is ignored — and it does not cover $watch handlers or $connectedCallback, which fail loudly on their own.

適用時にthrowするバインディング — パスgetterやフィルタが投げた、構造ディレクティブが失敗した — はすでに隔離されていた: バッチの残りは適用され、何もロールバックされず、失敗はconsole.errorとDevToolsへ行く。ルートstateに$errorCallback(error, info)を宣言すれば、その報告があなたに届く。infoは{ path, bindingType, node }で、pathはdata-wcsに書かれたままワイルドカードも保つ。thisは書き込み可能なstateプロキシなので、定石はメッセージをstateに書いて他と同じように描画すること。失敗したバインディングごとに1回、$updatedCallbackの後に走り、awaitされず、自身の例外も隔離されるのでフックがdrainを道連れにすることはない。DevToolsは変わらずstate:binding-apply-errorを受け取る。ルート専用 — ボリュームでの宣言は無視される — で、$watchハンドラや$connectedCallbackは対象外。それらは独自に大声で失敗する。

  • Getter, Filter, Directive
  • path As Written
  • After $updatedCallback, Not Awaited
  • Root-only, DevTools Still Sees It
v2.2.0 <wcs-media-query>

Dark mode is a boolean now

What if matchMedia was a tag?

A new I/O node. <wcs-media-query query="(prefers-color-scheme: dark)" data-wcs="matched: isDark"> wraps window.matchMedia and publishes matched / media / supported through one wcs-media-query:change event, with :state(matched) / :state(supported) reflected for CSS. A query that only changes styling still belongs in a stylesheet; this is for the answer that has to reach logic — a theme default, pausing a <wcs-raf> loop under prefers-reduced-motion, swapping a table for cards below a breakpoint, detecting (display-mode: standalone) for a PWA. Changing query while connected re-subscribes, generation-guarded so a stale list can never write, and old-Safari addListener is handled. The output is matched, not matches, because Element.prototype.matches() already exists on every element and a wc-bindable property is read straight off the Shell.

新しいI/Oノード。<wcs-media-query query="(prefers-color-scheme: dark)" data-wcs="matched: isDark">はwindow.matchMediaを包み、matched / media / supportedを1つのwcs-media-query:changeイベントで公開し、CSS向けに:state(matched) / :state(supported)を反映する。スタイルだけを変えるクエリは今までどおりスタイルシートに置けばいい。これは答えがロジックに届く必要がある場合のためだ — テーマの既定値、prefers-reduced-motion下で<wcs-raf>ループを止める、ブレークポイント以下でテーブルをカードに替える、PWAの(display-mode: standalone)検出。接続中のquery変更は再購読し、世代ガードで古いリストは決して書き込めない。旧SafariのaddListenerも扱う。出力名がmatchesではなくmatchedなのは、Element.prototype.matches()がすべての要素にすでに存在し、wc-bindableのプロパティはShellから直接読まれるからだ。

  • matched / media / supported
  • Logic, Not Styling
  • Re-subscribes, Generation-guarded
  • matched, Not matches
v2.2.0 trusted-types wcstack

Signed only what you wrote

What if a strict CSP could stay strict?

Pages enforcing require-trusted-types-for 'script' now work with state (innerHTML: bindings), router (layout templates), fetch (target= HTML replace) and worker (new Worker(src)). The split is the point: wcstack signs only strings the page author wrote — a <wcs-layout> template, a worker src — with one shared policy named wcstack, and never signs remote data: an innerHTML: value or a fetched HTML body needs an adopter-supplied sanitizing policy, injected through a global slot or setTrustedTypesPolicy(), and that injected policy applies even on engines without Trusted Types, so a sanitizer never degrades to a pass-through. DCC definition no longer has a sink at all — the shadow tree is cloned node by node instead of round-tripping through innerHTML. Verified against an enforcing Chromium, which found two things: a blocked target= injection now reports instead of throwing (an automatic fetch had nobody to catch the rejection), and a refused wcstack policy with an injected fallback warns once instead of also logging an error.

require-trusted-types-for 'script'を強制するページが、state(innerHTML:バインディング)、router(レイアウトテンプレート)、fetch(target=のHTML置換)、worker(new Worker(src))で動くようになった。要点は線引きだ: wcstackが署名するのはページ作者が書いた文字列だけ — <wcs-layout>のテンプレート、workerのsrc — で、wcstackという1つの共有ポリシーを使う。そしてリモートデータには決して署名しない: innerHTML:の値やfetchしたHTML本文には採用側が用意するサニタイズポリシーが必要で、グローバルスロットかsetTrustedTypesPolicy()で注入する。注入されたポリシーはTrusted Typesの無いエンジンでも適用されるので、サニタイザが素通しに退化することはない。DCC定義にはもうsinkが無い — shadow treeはinnerHTMLを往復せずノード単位で複製される。強制モードのChromiumで検証し、2つ見つかった: ブロックされたtarget=の注入はthrowせず報告するようになり(自動fetchのrejectionは誰も受け取れなかった)、wcstackポリシーが拒否され注入フォールバックがある場合はエラーも出さず一度だけ警告する。

  • Author Strings Signed
  • Remote Data Never
  • One Policy, Four Packages
  • Blocked Means Reported
v2.2.0 wcs/default-getter-mismatch

A quiet page, made loud

What if a page that went silent told you why?

A two-way binding on a static wcBindable property that omits getter writes e.detail to state — the protocol’s default. Two recent issues were diagnosed by staring at a page that had simply gone quiet: the element dispatched a plain Event with no detail, or wrapped it as { value: … } while the property held a scalar. The runtime now warns once per element and property when detail cannot be what the property holds: detail is undefined while the property has a value, or detail is an object carrying a <propName> key while the property is not an object. The write is still applied as-is — this is a diagnostic, not a repair — and occurrence properties (semantics: "event") are exempt. Declare an explicit getter to keep reading the property, and the warning has nothing to say.

getterを省いたstatic wcBindableプロパティへの双方向バインディングは、e.detailをstateに書く — プロトコルの既定だ。最近の2件のissueは、ただ黙ってしまったページを睨んで診断された: 要素がdetailの無い素のEventを投げていた、あるいはプロパティがスカラーなのに{ value: … }で包んでいた。ランタイムはいま、detailがプロパティの持つ値ではありえないとき、要素とプロパティごとに一度だけ警告する: プロパティに値があるのにdetailがundefined、あるいはプロパティがオブジェクトでないのにdetailが<propName>キーを持つオブジェクト。書き込みはそのまま適用される — これは診断であって修復ではない — し、発生プロパティ(semantics: "event")は対象外。明示的なgetterを宣言してプロパティを読み続ければ、警告には言うことがない。

  • Once Per Element and Property
  • undefined detail, Valued Property
  • { value } Wrapper Caught
  • Write Unchanged, Events Exempt

The Core Insight

The only contract is a path string

No hooks. No imports. No glue code.

フックなし。インポートなし。グルーコードなし。

In every existing framework, the component is where UI meets state. Even with external stores, you still write glue code inside the component to pull state in. State and UI always couple through JavaScript.

wcstack takes a different path. Literally. The only contract between UI and state is a path string — user.name, cart.items.*.subtotal, cart.total. The component's JavaScript doesn't contain a single line that references state. The HTML alone describes every data dependency — the same idea as a REST URL: a simple string contract, no shared code.

State   ← "user.name" →  UI          Path binds the two layers
Comp A  ← "cart.total" → Comp B      Mounted path crosses components
Loop    ← "items.*" →    Template    Wildcard abstracts the index

UIと状態を結ぶ唯一の契約はパス文字列。UIを作り直しても状態に触れなくていい。状態をリファクタリングしてもDOMに触れなくていい。HTMLを読めばすべてが分かる。

One protocol behind them all: wc-bindable

Every I/O node exposes a static manifest — observable properties, settable inputs, invocable commands — so any binding core can discover and wire it generically. Since v1.24.0 each observable also declares its semantics — state, event, or handle — so a generic adapter can tell a current value from an occurrence. <wcs-state> and @wcstack/signals speak it natively; thin adapters connect React, Vue, Svelte, and Solid.

index.html State 
<wcs-state>
  <script type="module">
    export default {
      taxRate: 0.1,
      cart: {
        items: [
          { name: "Widget", price: 500, quantity: 2 },
          { name: "Gadget", price: 1200, quantity: 1 }
        ]
      },
      removeItem(event, index) {
        this["cart.items"] = this["cart.items"].toSpliced(index, 1);
      },
      get "cart.items.*.subtotal"() {
        return this["cart.items.*.price"] * this["cart.items.*.quantity"];
      },
      get "cart.total"() {
        return this.$getAll("cart.items.*.subtotal", [])
          .reduce((a, b) => a + b, 0);
      },
      get "cart.grandTotal"() {
        return this["cart.total"] * (1 + this.taxRate);
      }
    };
  </script>
</wcs-state>

<template data-wcs="for: cart.items">
  <div>
    {{ .name }} &times;
    <input type="number" data-wcs="value: .quantity">
    = <span data-wcs="textContent: .subtotal|locale"></span>
    <button data-wcs="onclick: removeItem">Delete</button>
  </div>
</template>
<p>Grand Total: <span data-wcs="textContent: cart.grandTotal|locale(ja-JP)"></span></p>

Constraints

Rules of the Game

This project follows five strict constraints. They're what make it interesting.

5つの厳格な制約。これが面白さの源泉。

1

Single CDN import

One <script> tag. That's it. No npm, no bundler, no config.

scriptタグ1つ。npm不要、バンドラー不要、設定不要。

2

Features as custom tags

Everything is a custom element. If it can't be expressed as <wcs-something>, it doesn't belong here.

すべてはカスタム要素。<wcs-something>で表現できなければ、ここには属さない。

3

Initial load = tag definitions only

The script just registers custom elements. No initialization code, no bootstrap ritual.

スクリプトはカスタム要素を登録するだけ。初期化コードもブートストラップ儀式も不要。

4

Respect HTML semantics

Expressions live in data-* attributes and text nodes — places HTML already allows extension. The DOM structure and semantics stay intact.

式はdata-*属性とテキストノードに配置 — HTMLが拡張を許可する場所のみ。DOM構造とセマンティクスはそのまま。

5

Latest ECMAScript

We actively adopt cutting-edge JS features. No transpiling to ES5. This is the future, after all.

最新のJS機能を積極採用。ES5へのトランスパイルなし。未来のプロジェクトだから。

These rules sound simple. They're not. Respecting HTML semantics means you need to deeply understand where the spec allows extension — and where it doesn't. Building everything as custom tags means solving lifecycle, ordering, and communication within the Custom Elements spec. No dependencies means every algorithm is yours to write. And it all has to feel like it could be a browser built-in.

シンプルに聞こえるルールだが、実際は違う。HTMLセマンティクスを尊重するなら、仕様が拡張を許す場所と許さない場所を深く理解する必要がある。すべてをカスタムタグで構築するなら、Custom Elementsの仕様の中でライフサイクル・順序・通信を解決しなければならない。依存ゼロなら、あらゆるアルゴリズムを自分で書く。そしてそのすべてが「ブラウザ組み込みかもしれない」と感じさせなければならない。
