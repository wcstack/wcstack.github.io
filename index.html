v2.6.0 $eq(path, key)

One click, two rows

What if selecting a row re-evaluated only the rows whose answer changed?

A row getter that answers “is this row the selected one?” is where dependency tracking scales worst: get "items.*.selected"() { return this.$1 === this.selectedIndex; } makes every row depend on selectedIndex, so one click re-evaluates the whole list — 10,000 getters for a change that concerns two of them. this.$eq(path, key) reads path without a dependency and registers the row under its own key instead; a write to path then re-evaluates only the row that was selected and the row that becomes selected. Selecting one of 10,000 rows goes from 20 ms to 0.2 ms — the update queue drops from 10,001 entries to 3. The subscription is made only while a getter is being evaluated; from a method or a handler the same call simply returns the comparison. A row’s subscription is dropped with the row, and keys compare as Map keys — Object.is, except that +0 / -0 and NaN / NaN are one key, and with no coercion: a "2" typed into an input never matches the id 2. Keep the selection a primitive and write it directly — the row that was selected is found through the old value, and a getter as path is never written, so neither ever reaches the rows.

「この行は選択中か」を答える行getterは、依存追跡が最も効きにくい形だ: get "items.*.selected"() { return this.$1 === this.selectedIndex; }は全行をselectedIndexに依存させるので、1クリックでリスト全体が再評価される — 関係するのは2行なのに、getterは1万個。this.$eq(path, key)はpathを依存を張らずに読み、代わりに行をその行自身の鍵の下に登録する。pathへの書き込みで再評価されるのは、選択されていた行と選択される行だけだ。1万行から1行を選ぶ操作は20 msから0.2 msへ — 更新キューは10,001件から3件になる。購読が張られるのはgetterの評価中だけで、メソッドやハンドラから呼べば同じ呼び出しが比較結果を返すだけだ。行の購読は行とともに落ち、鍵はMapの鍵として比較される — Object.isだが+0 / -0とNaN同士は同じ鍵で、型変換はしない: 入力欄に打った"2"はid 2に一致しない。選択はプリミティブにして直接書くこと — 選択されていた行は古い値から探されるし、getterをpathにしても誰もそこには書かないので、どちらも行に届かない。

  • One Key Per Row
  • 20 ms → 0.2 ms at 10,000 Rows
  • A Plain Comparison Outside a Getter
  • Keep the Selection a Primitive
v2.6.0 $eqPath / $eqIndex

Selection that survives a sort

What if the selection followed the row, or the position — whichever you meant?

“Selected” has two meanings, and each gets its own form. this.$eqPath("selectedId", "items.*.id") keys each row on the value at keyPath — its wildcards resolve to this row — and reads that key without a dependency too, so sorting, replacing or removing rows never re-evaluates them: the selection stays with the id. this.$eqIndex("selectedIndex") keys on the row’s index (level picks the wildcard in a nested list) and, unlike reading $1, does not record the getter as index-dependent: the list diff re-keys moved rows itself, so removing a row re-evaluates at most two rows instead of every row after it. $eqIndex takes its key from a list row, so outside one it throws needs a list row scope. One rule comes with an untracked key: a row whose id changes in place is not re-evaluated by that change — use $eqPath for identities that do not change, and $eq with a tracked read (this.$eq("selectedId", this["items.*.id"])) when the key itself is live.

「選択」には2つの意味があり、それぞれに形がある。this.$eqPath("selectedId", "items.*.id")は各行をkeyPathの値 — ワイルドカードはこの行で解決される — で鍵付けし、その鍵も依存を張らずに読む。だから並べ替え・置き換え・削除で行が再評価されることはなく、選択はidに付いて行く。this.$eqIndex("selectedIndex")は行のindexで鍵付けし(levelはネストしたリストでのワイルドカード段を選ぶ)、$1を読むのと違ってgetterをindex依存に記録しない: 移動した行はリスト差分が自分で鍵を付け替えるので、1行削除で再評価されるのは後続の全行ではなく高々2行だ。$eqIndexは鍵をリスト行から取るので、行の外ではneeds a list row scopeでthrowする。追跡しない鍵には規則が1つ付く: idがその場で書き換わった行は、その変更では再評価されない — $eqPathは変わらない同一性に使い、鍵そのものが動くなら追跡付きの読みと$eqを組み合わせる(this.$eq("selectedId", this["items.*.id"]))。

  • Keyed on the Id
  • Keyed on the Index
  • Moved Rows Re-keyed by the Diff
  • Ids Must Not Change In Place
v2.6.0 wcs/v3-migration

3.0, named in advance

What if the next major told you what it will break — while this one still runs it?

3.0 ships without a compatibility layer. Instead, 2.6.0 names every form that 3.0 rejects or reads differently, and keeps running it the 2.x way. The syntax forms are checked when a binding is first parsed: a second # (value#ro#wo: — write value#ro,wo:), a value after else:, modifiers or filters on the keywords for / if / elseif / else / ..., radio#ro: and checkbox#ro: (today a property named radio that does nothing), an unterminated quote in filter arguments, more arguments than a filter takes, and unquoted true / false / null in eq / ne / defaults — 2.x compares or falls back to the string, so done|eq(true) never matches a boolean; 3.0 reads the typed value, and eq('true') keeps the text comparison. Each warning is printed once per form and site under [wcs/v3-migration], says what 3.0 does and what to write now, and changes nothing about how the binding runs. npx @wcstack/lint and the VS Code extension report the same forms with the same check, as wcs/v3-migration at info severity, so a --strict pipeline does not fail on a minor update; extra filter arguments stay under the existing wcs/filter-arity.

3.0は互換層を持たずに出る。代わりに2.6.0は、3.0が拒む書き方・読み方を変える書き方をすべて名指しし、動作は2.xのまま続ける。文法の形はバインディングを最初に解析するときに調べる: 2つ目の#(value#ro#wo: — value#ro,wo:と書く)、else:の後ろの値、キーワードfor / if / elseif / else / ...に付いた修飾子やフィルタ、radio#ro:とcheckbox#ro:(今はradioという名前の、何もしないプロパティ)、フィルタ引数の閉じていない引用符、フィルタが受け取る数を超える引数、そしてeq / ne / defaultsの引用符の無いtrue / false / null — 2.xは文字列と比べ、文字列を既定値にするので、done|eq(true)は真偽値に決して一致しない。3.0は型付きの値として読み、文字列で比べ続けるならeq('true')。警告は[wcs/v3-migration]のもとで書き方とサイトごとに1回だけ出て、3.0での扱いと今の書き換え先を示し、バインディングの動きは何も変えない。npx @wcstack/lintとVS Code拡張は同じ判定で同じ形をwcs/v3-migrationとしてinfoで報告するので、--strictのパイプラインがマイナー更新で落ちることはない。フィルタ引数の超過は既存のwcs/filter-arityのまま。

  • No Compatibility Layer in 3.0
  • Once Per Form and Site
  • What 3.0 Does, What to Write Now
  • Lint at Info — --strict Unaffected
v2.6.0 undefined → textContent

Values that change meaning

What if the console told you which values 3.0 will read differently?

Some forms are not in the markup at all — they are values that arrive at runtime, and only the runtime can name them. undefined reaching textContent / innerText / innerHTML keeps the previous text today — in a reused for row, the previous row’s — and empties it in 3.0: return "" or null for “no value”. undefined or null reaching an attr.* writes the text "undefined" / "null" and will remove the attribute; undefined into a style.* will clear it; 0n through truthy / falsy / defaults becomes falsy. On the API side, $resolve(path, indexes, undefined) reads today and will write undefined (the argument count decides), $resolve / $setAll writes through a readonly proxy will throw This state is readonly., a component writing through a #ro mount will fail with wcs/mount-readonly, and a component default shadowed by a partial mount will lose to the mount. One change lands now instead of being announced: $errorCallback on a volume or a mounted component, ignored silently until now, is named by the warning that lists the root-only keys — it still runs only on the root. A value warning fires only when the value actually arrives, so a clean console proves nothing about the paths your tests did not reach.

書き方の中には、マークアップにはまったく現れないものがある — 実行時に届く値で、名指しできるのはランタイムだけだ。textContent / innerText / innerHTMLに届いたundefinedは、今は前のテキストを残す — 使い回されたforの行では前の行のものを — が、3.0では空にする: 「値なし」には""かnullを返すこと。attr.*に届いたundefinedやnullは文字列"undefined" / "null"を書くが、3.0では属性を削除する。style.*へのundefinedは消去になり、truthy / falsy / defaultsを通る0nは偽になる。API側では、$resolve(path, indexes, undefined)は今は読み、3.0ではundefinedを書く(引数の個数で決まる)。readonlyのプロキシからの$resolve / $setAllの書き込みはThis state is readonly.をthrowし、#roマウントを通るコンポーネントの書き込みはwcs/mount-readonlyで失敗し、部分マウントに隠されたコンポーネントの既定値はマウントに負けるようになる。1つは予告ではなく今入る: ボリュームやマウントされたコンポーネントの$errorCallbackは、これまで黙って無視されていたが、ルート専用キーを挙げる警告で名指しされるようになった — 動くのは今もルートだけだ。値の警告はその値が実際に届いたときにしか出ない。だから静かなコンソールは何も証明しない — テストが通らなかった経路については。

  • Empty Text Empties in 3.0
  • Attributes Removed, Not Stringified
  • $resolve Counts Its Arguments
  • A Clean Console Proves Nothing
v2.6.0 items = []

A quarter of the garbage

What if clearing a long list didn’t wake the garbage collector?

Clearing 10,000 rows allocated 8.1 MB, and the young-generation collector ran inside the clear. The teardown walked its nodes with iterators and grew a per-node WeakSet of observer-skip marks — one entry for every node it took down. It now runs index loops and keeps one skip count per parent, so the same clear allocates 2.1 MB, with no scavenge inside the clear window (18–20 ms). No behaviour changes: the rows go exactly as they went; only the bookkeeping that takes them down got smaller.

1万行のクリアは8.1 MBを確保し、若い世代のGCがクリアの最中に走っていた。解体処理はイテレータでノードをたどり、オブザーバーを読み飛ばす印をノードごとのWeakSetに積み増していた — 取り外すノード1つにつき1件。いまはindexのループで回り、印は親ごとに1つのカウントで持つ。同じクリアの確保は2.1 MBになり、クリアの間にscavengeは走らない(18–20 ms)。挙動は変わらない: 行は以前とまったく同じように消え、小さくなったのはそれを取り外すための帳簿だけだ。

  • 8.1 MB → 2.1 MB
  • No Scavenge Inside the Clear
  • One Skip Count Per Parent
  • No Behaviour Change
v2.6.0 import { defineState }

Types without the runtime

What if importing a type helper cost only the helper?

A module that only calls defineState() — or only imports the types — kept the whole runtime: three registrations ran the moment the module was evaluated (the $watch and $streams runtimes and volume grafting), and a side effect at module level is something no bundler may drop. They are now installed by bootstrapState() and on each feature’s first use, idempotently, and the core no longer imports the DevTools module. A defineState-only import tree-shakes to about 0.3 KB gzip (it was 26.7 KB). No behaviour changes — every feature is wired before it can run. CI now holds the line on three fronts: the helper-only entry must stay under 1 KB gzip, auto.min.js within 3 % of the last release’s size, and the core’s reach into optional features at its recorded count.

defineState()を呼ぶだけ — あるいは型をimportするだけ — のモジュールも、ランタイムを丸ごと抱えていた: モジュールの評価時点で3つの登録($watchと$streamsのランタイム、ボリュームの接ぎ木)が走り、モジュールレベルの副作用はバンドラが捨ててよいものではないからだ。これらはいまbootstrapState()と各機能の初回利用で冪等に組み込まれ、コアはDevToolsのモジュールをもうimportしない。defineStateだけのimportはtree-shakeで約0.3 KB gzipになる(以前は26.7 KB)。挙動は変わらない — どの機能も動く前に組み込まれる。CIはいま3点で線を守る: ヘルパーだけのエントリは1 KB gzip未満、auto.min.jsは前リリース比3 %以内、コアから任意機能への依存は記録された数まで。

  • 0.3 KB gzip, Was 26.7 KB
  • Installed on First Use
  • No Behaviour Change
  • Size Gated in CI

The Core Insight

The only contract is a path string

No hooks. No imports. No glue code.

フックなし。インポートなし。グルーコードなし。

In every existing framework, the component is where UI meets state. Even with external stores, you still write glue code inside the component to pull state in. State and UI always couple through JavaScript.

wcstack takes a different path. Literally. The only contract between UI and state is a path string — user.name, cart.items.*.subtotal, cart.total. The component's JavaScript doesn't contain a single line that references state. The HTML alone describes every data dependency — the same idea as a REST URL: a simple string contract, no shared code.

State   ← "user.name" →  UI          Path binds the two layers
Comp A  ← "cart.total" → Comp B      Mounted path crosses components
Loop    ← "items.*" →    Template    Wildcard abstracts the index

UIと状態を結ぶ唯一の契約はパス文字列。UIを作り直しても状態に触れなくていい。状態をリファクタリングしてもDOMに触れなくていい。HTMLを読めばすべてが分かる。

index.html State 
<wcs-state>
  <script type="module">
    export default {
      taxRate: 0.1,
      cart: {
        items: [
          { name: "Widget", price: 500, quantity: 2 },
          { name: "Gadget", price: 1200, quantity: 1 }
        ]
      },
      removeItem(event, index) {
        this["cart.items"] = this["cart.items"].toSpliced(index, 1);
      },
      get "cart.items.*.subtotal"() {
        return this["cart.items.*.price"] * this["cart.items.*.quantity"];
      },
      get "cart.total"() {
        return this.$getAll("cart.items.*.subtotal", [])
          .reduce((a, b) => a + b, 0);
      },
      get "cart.grandTotal"() {
        return this["cart.total"] * (1 + this.taxRate);
      }
    };
  </script>
</wcs-state>

<template data-wcs="for: cart.items">
  <div>
    {{ .name }} &times;
    <input type="number" data-wcs="value: .quantity">
    = <span data-wcs="textContent: .subtotal|locale"></span>
    <button data-wcs="onclick: removeItem">Delete</button>
  </div>
</template>
<p>Grand Total: <span data-wcs="textContent: cart.grandTotal|locale(ja-JP)"></span></p>

        return role ? "/api/users?role=" + role : "/api/users";
      },
    };
  </script>
</wcs-state>

<wcs-fetch data-wcs="url: usersUrl; value: users; loading: loading"></wcs-fetch>

<template data-wcs="if: loading">
  <p>Loading...</p>
</template>
<template data-wcs="for: users">
  <div data-wcs="textContent: .name"></div>
</template>

Constraints

Rules of the Game

This project follows five strict constraints. They're what make it interesting.

5つの厳格な制約。これが面白さの源泉。

1

Single CDN import

One <script> tag. That's it. No npm, no bundler, no config.

scriptタグ1つ。npm不要、バンドラー不要、設定不要。

2

Features as custom tags

Everything is a custom element. If it can't be expressed as <wcs-something>, it doesn't belong here.

すべてはカスタム要素。<wcs-something>で表現できなければ、ここには属さない。

3

Initial load = tag definitions only

The script just registers custom elements. No initialization code, no bootstrap ritual.

スクリプトはカスタム要素を登録するだけ。初期化コードもブートストラップ儀式も不要。

4

Respect HTML semantics

Expressions live in data-* attributes and text nodes — places HTML already allows extension. The DOM structure and semantics stay intact.

式はdata-*属性とテキストノードに配置 — HTMLが拡張を許可する場所のみ。DOM構造とセマンティクスはそのまま。

5

Latest ECMAScript

We actively adopt cutting-edge JS features. No transpiling to ES5. This is the future, after all.

最新のJS機能を積極採用。ES5へのトランスパイルなし。未来のプロジェクトだから。

These rules sound simple. They're not. Respecting HTML semantics means you need to deeply understand where the spec allows extension — and where it doesn't. Building everything as custom tags means solving lifecycle, ordering, and communication within the Custom Elements spec. No dependencies means every algorithm is yours to write. And it all has to feel like it could be a browser built-in.

シンプルに聞こえるルールだが、実際は違う。HTMLセマンティクスを尊重するなら、仕様が拡張を許す場所と許さない場所を深く理解する必要がある。すべてをカスタムタグで構築するなら、Custom Elementsの仕様の中でライフサイクル・順序・通信を解決しなければならない。依存ゼロなら、あらゆるアルゴリズムを自分で書く。そしてそのすべてが「ブラウザ組み込みかもしれない」と感じさせなければならない。
