What's New

Shipped in v4.0.0 → v4.2.0

4.0 replaces the engine inside @wcstack/state — a smaller core and faster updates behind the same markup: auto.min.js goes from 88.0 to 47.7 KB gzip, and the CPU-weighted geometric mean on the official js-framework-benchmark is 1.07, against 1.44 for 3.5.4. Most of what breaks is what 3.5 announced, and there is no compatibility layer: upgrade to 3.5, clear its warnings, then move every @wcstack/* package to 4.0 at once — @wcstack/server together with the client — following the migration table and the 3.x → 4.0 migration guide. The VS Code extension ships the 4.0 rules as 2.0.0; keep 1.21.x, @wcstack/lint 3.5 and @wcstack/typescript 3.5 for 3.x projects. v4.0.1 comes from writing the tutorial: a class: or attr: without a name is refused by name (#122), and the lint stops reporting the fields of a list a getter returns and reports an unknown filter as an error. v4.0.2 comes from Part 2: the lint learns the shape of data loaded from outside from a JSDoc type, and reports a <wcs-storage> binding that would not save (wcs/input-nested-write, wcs/storage-init-seed). v4.0.3 comes from Part 3: the lint also catches a storage binding that forgets #init=element and a <wcs-fetch> body sent only once, and checks pinned URLs. v4.0.4, also from Part 3: a <wcs-outlet> placed away from its <wcs-router> stayed empty without a word — the router now warns about it, and so does the lint. v4.1.0 comes from four seam apps — apps written from the documents alone to find what tests miss: route guards that redirect without trapping Back, a confirmation before leaving unsaved changes (leaveConfirm), <wcs-network offline>, view transitions only for list and branch changes, and keyed signals rows that see their current item. v4.1.1 puts those apps in the repository's examples, each with a real-browser test, and fixes what that found: the lint now knows <wcs-network offline>. v4.2.0 settles what those apps left open: leaving a page with unsaved changes asks with the page's own message, the filters format dates and money (date(en-US,medium), currency(JPY)), and the lint sees a forgotten #prevent and an in-place change through an alias. The numbers are in Performance, the rest in the version notes of the state page.

v4.0.0 onclick#direct,stop: save

One listener per event type

What if a thousand rows of buttons needed one click listener, not a thousand?

on*: bindings of eleven common event types — click, input, change, submit, keydown, … — are delegated: one listener per type sits on the root the state binds and runs the handlers of the elements the event passed, innermost first. event.currentTarget is that root, so find the element with event.target.closest(…) or use the loop index, and an ancestor that calls stopPropagation() keeps the handlers inside it from running. on*#direct: keeps the 3.x listener on the element for one binding.

よく使う11種類のイベント — click・input・change・submit・keydownなど — のon*:バインディングは委譲される: 種類ごとに1つのリスナーがstateのバインドするルートに置かれ、イベントが通った要素のハンドラを内側から順に走らせる。event.currentTargetはそのルートなので、要素はevent.target.closest(…)で探すかループのインデックスを使う。stopPropagation()を呼ぶ祖先は、その内側のハンドラを走らせない。on*#direct:はバインディング1つについて、3.xと同じく要素にリスナーを付ける。

  • 11 Event Types Delegated
  • currentTarget Is the Root
  • #direct Opts One Binding Out
  • Two-Way Stays on the Element

v4.0.0 this["items.0"] = item

A row stays where it is

What if writing a list element changed what that row shows — and nothing moved?

Writing a list element (this["items.0"] = …) replaces the value at that position: the row stays where it is, with its focus and other DOM state, and everything derived below it is computed again. To move rows, assign a new array — rows follow their objects by identity. for: takes no filters (#121): loop over a getter that returns the list, and writes through its rows reach the source (#365). A numeric segment is an index only under an array: usersById.42.name is a key (#382).

リストの要素への書き込み(this["items.0"] = …)はその位置の値を置き換える: 行はその場にとどまり、フォーカスなどのDOMの状態もそのままで、その下で導かれるものは計算し直される。行を動かすには新しい配列を代入する — 行は同一性でオブジェクトについていく。for:はフィルタを取らない(#121): リストを返すgetterの上で回せば、その行を通した書き込みは元のリストに届く(#365)。数値の区間が添字になるのは配列の下だけで、usersById.42.nameはキーだ(#382)。

  • Element Writes Replace in Place
  • Reorder by a New Array
  • for: Over a Getter, Not a Filter
  • Writes Reach Filtered Copies

v4.0.0 "items.*.price"(cur, prev, i)

Watches that need no for:

What if a row watch fired for every row that changed — rendered or not?

A row watch is headless now: $watch: { "items.*.price"(cur, prev, i) { … } } fires for a list the page does not render, where 3.x fired it zero times. A watch on a row getter is evaluated eagerly for every row, with a real prev, so keep it cheap. Assigning a whole array fires only the rows that came in (#389), and a $watch → $stream loop stops after about 16 laps instead of freezing the page.

行のwatchはいまヘッドレスだ: $watch: { "items.*.price"(cur, prev, i) { … } }は、ページが描いていないリストでも発火する(3.xでは一度も発火しなかった)。行getterへのwatchは全行について先行して評価され、prevも本当の前の値になるので、軽く保つこと。配列全体の代入が発火させるのは新しく入った行だけで(#389)、$watch → $streamのループはページを止めずに約16周で打ち切られる。

v4.0.0 onclick: cart.checkout

Volumes hold data, components run their own

What if a module held only its data — and a component ran everything it declares?

A volume (<wcs-state mount="cart">) holds data, getters, setters and methods, and its methods are reachable by path — onclick: cart.checkout. One that declares $watch, $listKeys, $renderedCallback, $behavior or $features, or carries a data-wcs, is not grafted: declare those on the root with full paths. A mounted component goes the other way: it runs its own $listKeys, tokens, $on and $errorCallback, and a host inserted by code is wired when its <wcs-state bind-component> connects.

v4.0.0 <wcs-ssr version="4.0.0">

Server and client move together

What if a server-rendered page hydrated every row it drew — nested ones too?

4.0 writes a new server output — rows, branches and text bindings marked with comments, no data-wcs-ssr-id or props table — and the client adopts the server’s rows and branches where they are, nested ones included. The output is not compatible across 3.x and 4.0: a 4.0 client discards a 3.x snapshot with one warning and renders on the client, and a 4.0 server with a 3.x client is not supported. Deploy @wcstack/server 4.0 with the 4.0 client, purge HTML cached from 3.x, and keep the comments (removeComments breaks hydration).

4.0は新しいサーバー出力を書く — 行・枝・テキストバインディングはコメントで印が付き、data-wcs-ssr-idもプロパティの表も無い — そしてクライアントはサーバーの行と枝を、入れ子のものも含めて、その場で引き取る。出力は3.xと4.0の間で互換が無い: 4.0のクライアントは3.xのスナップショットを警告1つとともに捨ててクライアントで描き、4.0のサーバーと3.xのクライアントの組み合わせはサポートされない。@wcstack/server 4.0を4.0のクライアントと一緒にデプロイし、3.xでキャッシュしたHTMLを捨て、コメントは残すこと(removeCommentsはハイドレーションを壊す)。

v4.0.0 <wcs-wakelock data-wcs="active: awake">

An input is a property

What if a false written to a tag stayed false — as the element understands it?

State writes a custom element’s wc-bindable input to its property only; reflecting it to the attribute is the element’s job in its setter. 3.x’s copy turned a false into "false", which switched on <wcs-wakelock active> and every manual — an element of your own that relied on state writing its attribute needs a setter that reflects it. The I/O nodes handle null (removes the attribute) and undefined (restores the initial one) instead of opening "undefined", and the router, <wcs-defined>, <wcs-throttle>, <wcs-wakelock>, <wcs-ws> and DevTools bring fixes.

The Core Insight

The only contract is a path string

No hooks. No imports. No glue code.

フックなし。インポートなし。グルーコードなし。

In every existing framework, the component is where UI meets state. Even with external stores, you still write glue code inside the component to pull state in. State and UI always couple through JavaScript.

wcstack takes a different path. Literally. The only contract between UI and state is a path string — user.name, cart.items.*.subtotal, cart.total. The component's JavaScript doesn't contain a single line that references state. The HTML alone describes every data dependency — the same idea as a REST URL: a simple string contract, no shared code.

State   ← "user.name" →  UI          Path binds the two layers
Comp A  ← "cart.total" → Comp B      Mounted path crosses components
Loop    ← "items.*" →    Template    Wildcard abstracts the index

UIと状態を結ぶ唯一の契約はパス文字列。UIを作り直しても状態に触れなくていい。状態をリファクタリングしてもDOMに触れなくていい。HTMLを読めばすべてが分かる。

One protocol behind them all: wc-bindable

Every I/O node exposes a static manifest — observable properties, settable inputs, invocable commands — so any binding core can discover and wire it generically. Since v1.24.0 each observable also declares its semantics — state, event, or handle — so a generic adapter can tell a current value from an occurrence. <wcs-state> and @wcstack/signals speak it natively; thin adapters connect React, Vue, Svelte, and Solid.

すべてのI/Oノードは静的マニフェスト(properties / inputs / commands)を公開。v1.24.0からは各observableがsemantics(state / event / handle)も宣言し、汎用アダプタが現在値と発生を区別できる。stateとsignalsはネイティブ対応、薄いアダプタでReact / Vue / Svelte / Solidからも使える。

      get "cart.items.*.subtotal"() {
        return this["cart.items.*.price"] * this["cart.items.*.quantity"];
      },
      get "cart.total"() {
        return this.$getAll("cart.items.*.subtotal", [])
          .reduce((a, b) => a + b, 0);
      },
      get "cart.grandTotal"() {
        return this["cart.total"] * (1 + this.taxRate);
      }
    };
  </script>
</wcs-state>

<template data-wcs="for: cart.items">
  <div>
    {{ .name }} &times;
    <input type="number" data-wcs="value: .quantity">
    = <span data-wcs="textContent: .subtotal|locale"></span>
    <button data-wcs="onclick: removeItem">Delete</button>
  </div>
</template>
<p>Grand Total: <span data-wcs="textContent: cart.grandTotal|locale(ja-JP)"></span></p>

Constraints

Rules of the Game

This project follows five strict constraints. They're what make it interesting.

5つの厳格な制約。これが面白さの源泉。

1

Single CDN import

One <script> tag. That's it. No npm, no bundler, no config.

scriptタグ1つ。npm不要、バンドラー不要、設定不要。

2

Features as custom tags

Everything is a custom element. If it can't be expressed as <wcs-something>, it doesn't belong here.

すべてはカスタム要素。<wcs-something>で表現できなければ、ここには属さない。

3

Initial load = tag definitions only

The script just registers custom elements. No initialization code, no bootstrap ritual.

スクリプトはカスタム要素を登録するだけ。初期化コードもブートストラップ儀式も不要。

4

Respect HTML semantics

Expressions live in data-* attributes and text nodes — places HTML already allows extension. The DOM structure and semantics stay intact.

式はdata-*属性とテキストノードに配置 — HTMLが拡張を許可する場所のみ。DOM構造とセマンティクスはそのまま。

5

Latest ECMAScript

We actively adopt cutting-edge JS features. No transpiling to ES5. This is the future, after all.

最新のJS機能を積極採用。ES5へのトランスパイルなし。未来のプロジェクトだから。

These rules sound simple. They're not. Respecting HTML semantics means you need to deeply understand where the spec allows extension — and where it doesn't. Building everything as custom tags means solving lifecycle, ordering, and communication within the Custom Elements spec. No dependencies means every algorithm is yours to write. And it all has to feel like it could be a browser built-in.

シンプルに聞こえるルールだが、実際は違う。HTMLセマンティクスを尊重するなら、仕様が拡張を許す場所と許さない場所を深く理解する必要がある。すべてをカスタムタグで構築するなら、Custom Elementsの仕様の中でライフサイクル・順序・通信を解決しなければならない。依存ゼロなら、あらゆるアルゴリズムを自分で書く。そしてそのすべてが「ブラウザ組み込みかもしれない」と感じさせなければならない。
